# Migration log: r3d → DiligentEngine

Record of how each completed phase actually went — what landed, what broke, how it was found, what was verified against what. **This is history, not instructions.** Read the section for an area before working in it; do not read it end to end.

The working document — current status, the rules that must not be broken, and what is still planned — is [DILIGENT_MIGRATION.md](DILIGENT_MIGRATION.md). ### Phase 3 — sub-phase split

Same shape as Phase 2: each one builds, runs and is screenshot-verified against the R3D build before the next starts.

- **3.a Backend skeleton** ✅ — device attached to raylib's GL context, offscreen scene target, overlay brackets, compositing. Every resource method is a stub, so the viewport shows background + editor grid and nothing else.
- **3.b Geometry & first PSO** ✅ — vertex/index buffers, the cube primitive, per-frame and per-draw constant buffers, a first HLSL shader. Milestone: a cube framed identically under both backends.
- **3.c Forward PBR** ✅ — textures, material SRB, one directional light. This is the plan's stated Phase 3 milestone ("a textured lit cube renders equivalently via both backends").

⚠️ **3.c is the last sub-phase where screenshot-diffing against R3D is the verification method** (decided after the 3.b review). Nothing past textures and basic lighting was ever built on top of r3d on a real scene, so from Phase 4 on there is no R3D reference to diff *against* — a diff would only be comparing Diligent to an empty half of the picture. **Consequence: the "screenshot-diff the same test scene under R3D vs Diligent" line in the Verification section applies to Phase 3 only.** Phases 4–8 need the substitute the plan already names for Phases 10–11: verify against known-good reference output (a public glTF sample, a reference image of the technique) and against the scene's own expected behaviour. **That open question is now answered**: once diffing stops the R3D backend is carried purely so the tree stays runnable, so its deletion was pulled out of Phase 9 into the new Phase 3.6.

### Phase 3 checklist

- [x] **3.a Backend skeleton.** `rendering/backends/diligent/diligentRenderer.{h,cpp}`. `AttachToActiveGLContext` with `Window.hWnd` left null (spike 0.3's finding), an offscreen colour+depth `ITexture` pair as the scene target, `beginScene` clearing to the environment's background colour, and `drawSceneTexture` blitting the colour texture's GL name as a raylib `Texture2D`. `modules/engine/CMakeLists.txt` links `Diligent-GraphicsEngineOpenGL-static` **and `Diligent-Common`** for the Diligent backend — `Diligent-Common` (which carries `RefCntAutoPtr`) is a *private* dependency of the GL engine target, so its include directory is not propagated by linking the engine target alone. **Verified**: `BreadEditor` builds 711/711 exit 0 in a second build directory, runs 22 s on the Capsule + directional-light scene with zero Diligent errors or warnings logged, and the viewport screenshot matches the R3D build's background colour, grid and camera framing exactly (only the capsule is missing, since draw is still a stub).

**Sub-phase 3.a decisions** (both are inside the backend — `IRenderer` is unchanged — but they are shape decisions, not details):

- **The editor's overlay pass draws into a raylib framebuffer built over Diligent's own two textures.** `rlLoadFramebuffer()` + `rlFramebufferAttach` on the colour and depth textures' GL names, so `beginSceneOverlay`'s `BeginTextureMode` puts rlgl's grid and gizmos in the exact attachments Diligent rendered into — which is what 2.d's depth trap requires. ⚠️ **`rlUnloadFramebuffer` deletes whatever texture it finds on the depth attachment** (verified in `lib/engine/rlgl.h`), and that texture belongs to Diligent; the depth attachment is therefore detached before the FBO is released. Colour attachments are not touched by rlgl, so only depth needs this.
- **The game renders into the same offscreen target and gets blitted, rather than rendering to the backbuffer directly.** `AttachToActiveGLContext` deliberately creates no swap chain ("the application is responsible for presenting the main frame buffer"), so there is no Diligent-side backbuffer to target with a known format. `endScene` blits full-screen when no caller sized a target, which keeps `IRenderer`'s "no explicit target → backbuffer" contract intact. Side effect, deliberate: the target now follows the window size, where `R3D_Init` was handed 800×600 before `MaximizeWindow()` and never resized.

**Matrix convention — decided in 3.a, implemented in 3.b.** Diligent's `float4x4::Projection` is **left-handed**, and its math is row-vector; the engine is right-handed raylib/raymath with column-vector `Matrix`. Rather than converting, the CPU side keeps building view/projection with `MatrixLookAt`/`MatrixPerspective` and uploads the 16 floats, with HLSL written column-vector (`mul(M, v)`) so HLSL's default column-major packing lines up with what rlgl itself uploads. This is **not just convenience: it is required by the overlay**, which depth-tests rlgl geometry against the scene's depth buffer and therefore needs the scene written in rlgl's own `[-1, 1]` NDC depth range. A future Vulkan/D3D backend changes only the CPU-side projection (to `[0, 1]`); the shaders stay as they are.

⚠️ **"The 16 floats" means `MatrixToFloatV(m).v`, not the bytes of the `Matrix` struct — they are transposes of each other.** raylib declares `Matrix` as `float m0, m4, m8, m12; float m1, m5, ...`, so its *storage* order is row-major, while `MatrixToFloatV` reorders to `m0, m1, m2, m3, ...` — the column-major array OpenGL takes with `transpose = false`, and the one `glUniformMatrix4fv` gets everywhere in rlgl. A `memcpy` of the struct would upload the transpose and silently produce a wrong (but plausible-looking) transform. Confirmed on the GLSL side too: the HLSL2GLSL converter only emits `layout(row_major)` when the source asks for it with `#pragma pack_matrix(row_major)`, and its own header notes "by default, all matrices in both HLSL and GLSL are column major".

⚠️ **The GL context is exactly 3.3, and that is raylib's decision, not ours.** The runtime log reads `Attached to OpenGL 3.3 context (3.3.0 NVIDIA 591.86)` followed by `Disabling separable shader programs` — the vendored `libraylib.dll` is built `GRAPHICS_API_OPENGL_33` and GLFW is asked for 3.3 core, so Diligent adopts that context as-is. Consequences for 3.b/3.c: the HLSL→GLSL converter emits `#version 330 core` (the version is derived from the device's actual GL version in `GLSLUtils.cpp`), and SSBOs, compute, and image load/store are unavailable. If DiligentFX's PBR path turns out to need 4.x, the fix is to rebuild the vendored raylib with `GRAPHICS_API_OPENGL_43` — not to work around it in the backend. **HLSL is usable on the GL backend**: DiligentCore links `Diligent-HLSL2GLSLConverterLib` into `Diligent-GraphicsEngineOpenGL-static` (this is a different target from the `HLSL2GLSLConverter` CLI tool that Phase 1 had to `EXCLUDE_FROM_ALL`).

- [x] **3.b Geometry & first PSO.** New backend-neutral `rendering/geometry/`: `meshData.h` (`MeshVertex` + `MeshData`) and `primitiveGenerator.{h,cpp}` (`generatePrimitive`, cube only so far). The Diligent backend gained a `MeshSlot` pool (immutable vertex + index buffer, index count), one `IPipelineState` + `IShaderResourceBinding` for opaque scene geometry, two `USAGE_DYNAMIC` constant buffers (per-frame view-projection, per-draw model), and a `_draws` queue. **Verified**: both backends build clean (exit 0), the editor and the standalone game run with zero Diligent errors or warnings logged, and the cube's silhouette in the editor viewport is pixel-identical between the two builds — same left/right edges, same bottom vertex, same top-face/front-face edge, same triangle seam across the front quad.

**Sub-phase 3.b decisions:**

- **The primitive generators are backend-neutral, under `rendering/geometry/`, not inside the Diligent backend.** They are pure CPU math with no API dependency, and Phase 5 writes the other nine there. Putting them under `backends/diligent/` would mean moving them in Phase 5 and would cost Phase 9 its "delete a directory plus one CMake branch" property. Cost accepted: they compile (unused) into an R3D build until Phase 9.
- **`MeshVertex` is position + normal + uv + `Vector3` tangent, and that is now the contract Phase 5's nine remaining generators write to.** The attribute *set* mirrors DiligentFX's `PBR_Renderer`, whose documented layout is `float3 Tangent : ATTRIB7` — **no handedness `w`**, the bitangent being derived as `cross(normal, tangent)`. Matching that now means the buffers can feed `PBR_Renderer` unchanged and the importer has one convention to hit; the cost is that `tangent` is written but unread until normal mapping lands.
- **Engine shaders are `.hlsl` files copied next to the executable** (`bread_copy_engine_shaders()` in the root `CMakeLists.txt`, `copy_directory` not the assets' copy-if-missing, since they are part of the binary's behaviour), loaded through `IEngineFactory::CreateDefaultShaderSourceStreamFactory` rooted at `GetApplicationDirectory() + "shaders"`. The alternative — DiligentFX's own approach, `convert_shaders_to_headers()` + `MemoryShaderSourceFactory`, which embeds shaders in the binary — was rejected for two reasons: Phase 11's hot-reload wants real files at runtime, and `convert_shaders_to_headers` is defined by DiligentCore's `BuildUtils.cmake`, which is not loaded yet when `add_subdirectory(modules/engine)` runs (DiligentCore is added after it, deliberately, for the zlib reason above). Revisit only if shipping a single self-contained exe becomes a goal.
- **`Diligent-GraphicsTools` is deliberately not linked.** Its `MapHelper` is the idiomatic way to write a dynamic buffer, but it is the only thing that would have been used from a whole static library; `IDeviceContext::MapBuffer`/`UnmapBuffer` through a five-line local helper does the same with no new dependency. Reconsider when something else in that library is actually needed.

**Three real traps found in 3.b, all of them runtime-only — "it builds" caught none of them:**

- ⚠️ **The HLSL→GLSL converter passes C-style casts straight through, and GLSL rejects them.** `mul((float3x3)g_Model, normal)` compiles as HLSL and fails at GL shader compile time with `error C7503: OpenGL does not allow C-style casts`. Diligent reports it clearly (it dumps the full generated GLSL), but only when the shader is created — there is no offline check. Written as `mul(g_Model, float4(normal, 0.0)).xyz` instead, which is also the naive normal transform (correct up to non-uniform scale, which the test scene now deliberately exercises visually). **General rule for every shader from here on: HLSL that is legal for D3D is not automatically legal through the converter** — casts, implicit conversions (`float4 v = 0;`), `float3` struct members and structs passed to functions are all called out in `HLSL2GLSLConverterImpl.hpp`'s "known issues" header comment. Read it before writing anything non-trivial.
- ⚠️ **Diligent's PSO leaves GL state that rlgl believes it still owns, and rlgl only issues the GL calls it thinks are needed.** The scene pipeline disables blending and enables the depth test; rlgl's own state model says the opposite outside a 3D pass. The visible symptom was the *entire editor UI* rendering its text as solid rectangles — the font atlas drawn with blending off — while the 3D overlay looked perfect, because `BeginMode3D` re-enables depth explicitly and blending does not matter for the grid. `yieldToRaylib()` now restores blending and the depth test alongside unbinding. **This generalizes: anything a future PSO sets that rlgl also tracks (cull mode, front face, scissor, depth writes, blend func) has to be restored there too.** Culling and depth writes currently match rlgl's defaults by coincidence, not by design.
- ⚠️ **`InvalidateState()` is needed *before* the Diligent pass, not only after it.** Spike 0.3 established the unbind/invalidate/flush sequence for handing the context back to raylib; the mirror case is just as real, because raylib has been drawing through the same context all the way from the previous `endScene`, so Diligent's cached GL state is stale by the time the scene pass starts.

**Two smaller things worth knowing:**

- The scene projection takes its near/far from `rlGetCullDistanceNear()`/`rlGetCullDistanceFar()` rather than hardcoding `0.01`/`1000`. The editor's overlay depth-tests against this target's depth buffer through raylib's own `BeginMode3D`, which uses those same values — a divergence would show up as grid lines cutting through geometry at the wrong depth.
- Aspect comes from the scene target, not the screen. Note that raylib's `BeginMode3D` derives its aspect from `GetScreenWidth/Height` regardless of the render texture it is drawing into, so the editor's overlay projection does *not* exactly match the scene's when the viewport panel is not the full window. This is pre-existing and identical under both backends, so it does not affect a screenshot diff — but it is the reason the grid and the scene can disagree by a fraction of a degree.

**The checked-in test scene gained a Cube node, and its transform is deliberately non-trivial** (position `{0, 0.5, 0}`, 30° about Y, scale `{1.5, 1, 1}`). A cube at the origin with an identity transform would have made the per-draw constant buffer untestable — the wrong model matrix and no model matrix at all look the same. With the transform, the silhouette comparison against R3D validates the whole `T * R * S` composition and the upload order in one shot. The Capsule and the glTF model still render nothing under Diligent, which is expected: their generators and the model path land in Phase 5. **3.c then gave the Cube the scene's three existing textures** (`scene_albedo.jpeg`, `scene_normal.png`, `scene_omr.png`) — without them nothing in the scene exercised the texture path at all, since the only textured node is the model Diligent cannot draw yet.

- [x] **3.c Forward PBR.** `scene.psh` became a metallic-roughness shader (Trowbridge-Reitz GGX, Smith with Schlick's k, Schlick Fresnel, glTF ORM packing), the backend gained a texture pool backed by DiligentTools' loader, four material texture slots on the pipeline, 1x1 fallback textures and a real light pool. `SceneFrameConstants` now carries the camera position, the light and the ambient term alongside the view-projection; `SceneDrawConstants` carries the model matrix and its inverse transpose. **Verified**: both backends build clean, editor and standalone game run with zero Diligent errors or warnings, and the textured cube's silhouette, UV placement and face-to-face shading match the R3D build. Measured against the R3D capture at the same pixels: editor chrome 245/245/245 and 201/201/201 in both, viewport background 130/130/130 in both.

**Sub-phase 3.c decisions:**

- **The shader is engine-owned, not DiligentFX's `PBR_Renderer` — deliberately, and only for now.** Spike 0.4 decided to drive `PBR_Renderer` directly, and that still stands for Phase 4/5. Adopting it inside 3.c would have meant taking on its PSO flags, its exact `PBRFrameAttribs`/`PBRPrimitiveAttribs` layouts and its SRB conventions in the same step as the first textures — with the GL 3.3 ceiling as an unquantified risk on top (parts of its shader tree reference `gl_DrawID` and structured buffers, which would force rebuilding the vendored raylib as `GRAPHICS_API_OPENGL_43`). ~60 lines of HLSL keeps 3.c's failure modes inside our own code. Phase 4 decides whether they get deleted.
- **Textures load through DiligentTools' `TextureLoader`, split across two threads the way the loader is built for.** `CreateTextureLoaderFromFile` needs no device, so it runs on the shared `WorkerPool` exactly where raylib's `LoadImage` used to; `ITextureLoader::CreateTexture(device, ...)` runs on first use, on the thread that owns the device. That is the same decode-then-upload shape the R3D backend already had, and it brings sRGB handling, mip generation and DDS/KTX for free — the reuse the plan's Phase 4 note predicted.
- **Material textures are `SHADER_RESOURCE_VARIABLE_TYPE_DYNAMIC` variables re-pointed per draw, not an SRB per material.** With no `MaterialHandle` yet (deferred to Phase 4 on purpose) there is nothing stable to key an SRB cache on, and a dynamic variable plus a `CommitShaderResources` between draws is what Diligent provides for exactly this. The variable pointers are resolved once at pipeline creation, since the lookup is by name and the draw loop would otherwise run it per material.
- **No sampler cache.** `IRenderDevice::CreateSampler` already de-duplicates by description (`RenderDeviceBase::CreateSamplerImpl` goes through `m_SamplersRegistry`), so each texture asking for its own is free. Combined texture samplers put the sampler on the *view*, which is what makes a per-texture filter/wrap reach the GPU at all.
- **The fallback textures reproduce `R3D_MATERIAL_BASE` exactly** — white albedo, flat normal, occlusion 1 / roughness 1 / metalness 0, no emission — so an untextured material shades the same under both backends rather than differing by a default nobody chose.

⚠️ **The 3.b comment about tangent handedness was wrong, and it is fixed.** It claimed the bitangent is `cross(normal, tangent)`. DiligentFX derives it the other way round — `float3 b = normalize(cross(t, n))` in `ShaderUtilities.fxh`, and `cross(Tangent, Normal)` in `RenderPBR.psh` — which is also what the cube generator actually produces and the direction v increases in. Left as written, every normal map's green channel would have been inverted.

**Three more pieces of GL state Diligent changes globally and rlgl knows nothing about.** All three are the same class as 3.b's blend/depth finding, all three were invisible until something drew, and all three needed raw GL to undo — so the backend now links `GLEW::glew`, the loader DiligentCore already initializes against the shared context (its `GLEW_STATIC` define and include directory are `PUBLIC`, and the function pointers are global, so linking the same static target is enough — no second `glewInit`).

- ⚠️ **Diligent binds a sampler object per texture unit, and a leftover one blacked out the entire editor UI.** rlgl uses no sampler objects at all and relies on each texture's own parameters; a bound sampler overrides them, and its mipmapped minification filter makes raylib's single-mip textures *incomplete*, which samples as opaque black. The symptom was total: every panel, every glyph, the whole chrome, while the 3D viewport still rendered. `yieldToRaylib()` now unbinds the sampler on every unit the material slots use. **Note that `InvalidateState()` does not help here** — it resets Diligent's *cache* of the GL state, not the GL state itself, which is the whole reason these restores have to be explicit.
- ⚠️ **Diligent leaves `GL_UNPACK_ROW_LENGTH` set to the stride of whatever it uploaded last, and that silently blanked every glyph in the editor.** `Texture2D_GL.cpp` sets it per upload (`SubresData.Stride / PixelSize`) and never restores it; raylib sets only `GL_UNPACK_ALIGNMENT` before its own uploads, because it has always been able to assume the default row length of 0. The 1x1 material fallbacks leave it at **1**, so raylib's next `glTexImage2D` walks its source one pixel per row — which reduces the font atlas to nothing. The symptom is unusually specific and worth recognizing: **panels, borders and icons all render correctly while text is completely absent**, because raygui draws its icons as rectangles through rlgl's default 1x1 texture (created at `InitWindow`, before Diligent existed) and the font atlas is the only thing the editor uploads itself. `restoreRaylibPixelStore()` now runs after every point Diligent is handed pixels — the fallbacks at startup and each texture upload in `finalizeTexture`. Note this one is *not* fixable in `yieldToRaylib()`: fonts are loaded during editor init, before any frame is yielded.
- ⚠️ **Diligent enables `GL_FRAMEBUFFER_SRGB` once at device creation and deliberately never turns it off** (`RenderDeviceGLImpl.cpp`: "this setting should be just set once and left that way"). That is sound for its own targets — the conversion is a no-op for non-sRGB formats — but raylib's colours are already encoded, so everything rlgl drew to the window was being gamma-encoded a second time. **This is the real explanation for the 3.a note that "the Diligent gray reads slightly lighter than r3d's for the same 130,130,130"** — it was not tonemapping. Measured: the viewport background read 189 with it on, and exactly 130 (r3d's own value) with it off.

**One real bug in the BRDF, worth knowing because the wrong form is the common one.** Writing the specular term as `D*G*F / max(4*nDotV*nDotL, eps)` and then multiplying the whole result by `nDotL` breaks the cancellation those two `nDotL`s are supposed to do: wherever the light only grazes a surface the clamp takes over and leaves a bright rim. Measured on the test cube's side face: 61/55/63 with the clamp, 0/0/2 without it. The term is now `D*G*F / (4*nDotV)` with `nDotL` applied to the diffuse lobe only, which is the same equation with nothing to clamp.

**Colour response is the one thing that does not match r3d, and it is now a project setting rather than a hardcoded choice.** The shader encodes its linear result before writing to the plain UNORM scene target. r3d's tonemap in the checked-in scene is mode `Linear` with exposure 1, so r3d writes linear values straight out and its lit surfaces read near-black (0-1 where a gamma-encoded pass reads 28-47 for the same dark albedo). Geometry, UVs, face-to-face shading, chrome and background all match exactly; only the surface response differs, because r3d is not gamma-correcting.

`ProjectSettings::outputColorSpace` (`OutputColorSpace::Gamma | Linear`, **defaulting to Gamma**) now decides it, and `IRenderer::setOutputColorSpace` carries it across the seam. Details worth knowing:

- **It is pushed from `Engine::initialize`, right after the validator, and not before.** `Renderer::initialize` runs several lines *earlier* than the project settings are loaded, so the renderer cannot read the value at construction. Consequence: editing the field in the inspector takes effect on the next launch, which the field's own comment says.
- **It reaches the shader as a constant, not a shader permutation** — one exponent in the frame block (`1/2.2` or `1.0`), so there is no PSO to rebuild when it changes. `pow(color, 1.0)` is a wasted instruction in Linear mode and that is the whole cost.
- **Adding the field does not break existing `.cnf` files.** `InspectorStruct::deserialize` guards every property with `if (node[prop.name])` ([inspectorObject.cpp:88](modules/engine/inspectorObject.cpp)), so a config written before the field existed simply keeps the C++ initializer — Gamma. Worth remembering as the general rule for adding settings: **new inspector fields are backward compatible; only removing or reordering enum values is not.**
- The R3D backend implements the call as a no-op, because what r3d writes is decided by the environment's own tonemap block, which already goes through `setEnvironment`.
- Known inconsistency in Linear mode, inherited rather than introduced: the background is cleared with the raw (already-encoded) colour while shading writes linear. That is exactly r3d's own behaviour, which is what the mode exists to reproduce. Gamma mode is the self-consistent one, and proper tonemapping belongs in front of the encode in Phase 7.

**The test scene is now a checked-in asset — the gap 2.a flagged is closed.** `games/example_game/assets/` carries `Root.nd`, `assets_registry.cnf`, `project_settings.cnf` and `global_light_settings.cnf`, so `CopyMissingAssets.cmake` seeds every build directory with the same scene and the same asset GUIDs. The scene is a Capsule primitive at `x = -3`, a transformed Cube primitive at the origin (added in 3.b, see below), the `scene.gltf` model (albedo + normal + ORM, 4096²) at `x = +3`, and a directional SunLight — one node per rendering path the migration has to keep working. `editor_settings.cnf` is deliberately *not* checked in (it is editor-local and was empty); the registry heals itself by re-adding it with a fresh GUID on first run, which is safe because nothing references it. **To update the scene, edit it in the editor and copy those four files back out of `bin/assets/game/`** — `copy_missing` only copies what is absent, so it will never overwrite build-directory state.

Getting there needed a real fix first, and it applies to any checked-in project, not just this scene:

- ⚠️ **The assets registry baked absolute paths, so it could only ever load on the machine and in the directory that wrote it.** `deserializeConfig` computed `_projectPath` correctly from the config file's own location and then immediately overwrote it with the serialized one, and every `File`/`Folder` carried a serialized absolute `_fullPath`. Checking that in would have produced a registry that resolves to `cmake-build-debug` on every machine — and when the paths do not exist, `removeUndefinedFoldersAndFiles` strips the whole tree, which loses exactly the GUIDs the scene's asset links resolve through. **Fixed by making the registry relocatable**: `_projectPath` and `_fullPath` are no longer serialized at all (they are fully derivable), the runtime `_projectPath` is kept, and `AssetsConfig::restoreFullPaths` rebuilds every absolute path from `_projectPath` + the still-serialized `_pathFromRoot` before the indexes are built. Old registries with the extra keys still load — the keys are simply not read — and are rewritten in the new form on first save, so no migration is needed. Verified by wiping `bin/assets/game/` in the Diligent build directory, re-seeding from source, and confirming the model and its three textures resolve to the same GUIDs under a completely different absolute path.
- One consequence worth knowing: a **binary built before this change crashes on a registry written after it** (`invalid node; first invalid key: "_projectPath"` — yaml-cpp throws on the missing key). New code reads old files fine; the reverse is not supported.
- `games/example_game/main.cpp`'s hardcoded camera moved from `{10, 1, 1}` to `{0, 2, 12}` looking at `{0, 0.5, 0}`, so the game frames the two objects side by side the way the editor viewport does instead of stacking them along its own view axis.

### Review pass between 3.a and 3.b

A code-quality review and a bug hunt were run over `rendering/`, `systems/`, `engine.cpp`, `editor.cpp` and the example game before starting 3.b. Everything below is fixed and verified (both backends build, editor and game screenshot-match their pre-fix captures on the checked-in scene, zero errors logged).

- ⚠️ **The relocatable-registry change from 3.a turned a latent bug into data loss, and that is now fixed.** `renameFile` / `renameFolder` / `moveFile` built a child's `_pathFromRoot` as `parent->_pathFromRoot + "\" + name`, but the root folder's `_pathFromRoot` is the display string `"Project Files"`, not a path — so anything renamed at the project root became `"Project Files\X"`. `renameFolder` also guarded on `folder->getDepth() == 0` when a top-level folder has depth **1**, so its guard never fired, and it never assigned `_fullPath` at all (making `renameInternal` a `rename(X, X)` no-op). While `_fullPath` was serialized this was cosmetic; once `_pathFromRoot` became the only source of truth, a single rename made the registry unloadable, which strips the tree and re-registers every file with **fresh GUIDs** — silently breaking every asset link in the scene. Fixed with one `childPathFromRoot(parent, name)` and one `toFullPath(pathFromRoot)` used at every site that assigns either field, so `_fullPath` is always derived and the two can no longer diverge.
- **`Logger` stored a `std::string_view` into raylib's rotating `TextFormat` buffer** (4 buffers), so every retained entry was garbage after four more log lines. Note this **invalidates what the 2.a notes claimed**: the function-local `static std::string` in `renderer.cpp` was not a workaround, because `Log()` re-wrapped the message through `TextFormat` regardless. `LogEntity::message` is now a `std::string`, which fixes every call site at once; the two statics are gone.
- **`Renderer::get()` no longer initializes on demand.** It was a second, invisible init path with different arguments, and for Diligent it would attach to a GL context that may not exist yet (failing several frames later) or resurrect the backend after `shutdown()`. It now throws, matching the `Logger::LogError` + `throw std::runtime_error` idiom already in `assetsConfig.cpp`. Both entry points call `Engine::initialize` first, so nothing legitimate reaches it.
- **`CreatePrimitiveCommand` ran its parameter panel on a detached thread** that dereferenced `this` (use-after-free after undo), queued a closure capturing the worker's stack `MeshPrimitiveData` **by reference** onto the main thread, called `IsKeyPressed` off the main thread, and raced on `isChangedFromEditor`. Rewritten synchronously: `Command` gained a `virtual void update()` ticked by `CommandsHandler::update()`, and the command owns its data in a `unique_ptr`. The ten near-identical switch arms collapsed into one `createData` factory, with the node name coming from `magic_enum::enum_name` (so "FreePoly Mesh" is now "FreePoly").
- **One decode thread was spawned per texture.** New `utils/workerPool.{h,cpp}`: a bounded pool (≤4 workers) shared by both backends, joined from `Engine::shutdown`. `TextureSlot` holds a `std::future<void>` instead of a `std::jthread` — ⚠️ **a dropped future does not wait, where the `jthread` destructor did**, so every path that frees or recycles a slot must wait on the job first; all of them already do, and the member carries a comment saying so.
- **`MeshRenderer`'s loaded state had four overlapping sources.** `_isLoaded` is gone — `isLoaded()` is now `_mesh.isValid() || _model.isValid()`, the handles being the authority that 2.b's zeroed-handle fix established. A new `_loadAttempted` latch stops a *failed* model load from re-importing the file every frame. `setGeneratedMesh` now clears `_meshAsset`, enforcing the "either a primitive or a model, never both" invariant the header already claimed, and the primitive path seeds one material when a scene file carries none (the draw path indexes slot 0 unconditionally). `MeshRendererSystem` unloads-then-loads once per frame, leaving `ResetChangedFromEditorSystem` the only clearer of `isChangedFromEditor`.
- **`getModelMaterialCount` takes a `ModelHandle` instead of a path.** It was the only seam method taking a filesystem path while owning no GPU resource, and in a Diligent backend it would have dragged assimp into the GPU backend purely to answer a question about a file — against the Phase 5/9 goal of scoping assimp to import time. `MeshAsset` now loads and destroys the model around the query; same work r3d did internally, only visible, and it runs once per newly registered model.
- Smaller: `EnvironmentSettings` passes by `const&` on `IRenderer` and both backends (const binds the bundle, not the blocks it refers to, so `applyDefaultEnvironment` still writes through); `cameraSystem.cpp` maps `ProjectionType` through a new `toRaylibProjection` instead of `static_cast<int>`, which only worked because the declaration order — a *serialization* contract — happened to match raylib's enum; `onFrameStart`/`onFrameEnd` test the two game render callbacks independently, where a module exporting only one used to get neither.
- **The Diligent backend binds and clears in `endScene`, not `beginScene`.** The engine pushes the environment (and with it the background colour) from a start-frame system that runs *after* `beginScene` returns, so the clear used the previous frame's colour. This is also where the collected draws will be submitted from 3.b on.

Still open, deliberately: `Material::unload()` tears down `TextureAsset`s other materials may share, so any inspector edit on a model re-imports it and re-decodes its textures — the right fix is refcounting in `TextureAsset`, not in the seam. Also unaddressed: a light on a *deactivated* node stays lit (`LightState::active` is unreachable because both the registry and `LightSystem` skip inactive nodes), and `CameraDirectorSystem` accumulates camera pointers across frames — both belong with Phase 6's light/camera work.

**Background colour will not match exactly until Phase 7.** 3.a clears to `EnvironmentSettings::background.color` raw, where r3d runs its background through tonemapping and colour grading — so the Diligent gray reads slightly lighter than r3d's for the same `130,130,130`. Compare geometry, framing and shading for now; colour-exact diffs are a Phase 7 expectation.

### Phase 2 — agreed shape (decided before any code was written; don't re-litigate silently)

- **Backend switch is compile-time, not runtime.** `BREAD_RENDER_BACKEND` CMake cache option (`R3D` | `Diligent`, defaults to `R3D`), which sets `BREAD_RENDER_BACKEND_R3D=1` / `BREAD_RENDER_BACKEND_DILIGENT=1` as a `PUBLIC` compile definition on `BreadEngine` (so editor and game inherit it). Exactly one backend's `.cpp` files are compiled — `modules/engine/CMakeLists.txt` filters `rendering/backends/` out of the `GLOB_RECURSE` and adds back only the selected directory. Rationale: r3d gets deleted outright, so the inactive backend must not survive as dead code in the shipped game. **Consequence for QA: screenshot-diffing R3D vs Diligent means two build directories, not an env var** — which applied through Phase 3 and stops there, see the ⚠️ note under the Phase 3 sub-phase split. The switch itself outlives its purpose in Phase 3.6, where deleting r3d leaves it single-valued.
- **Sub-phase order** (each one builds, runs and is verified before the next starts): **2.a lights** ✅ · **2.b resources & draw** ✅ · **2.c environment/skybox** ✅ · **2.d frame lifecycle & call sites** ✅.
  Textures/materials and meshes/draw were originally planned as two separate sub-phases. They were merged into 2.b because they cannot be split: a material only reaches the GPU through a draw call, so doing materials first would have meant writing a temporary `MaterialData → R3D_Material` adapter for `meshRendererSystem` and deleting it one sub-phase later.
- **`Material` stays a value struct**, holding engine-native material data plus `TextureHandle`s; the renderer translates it at draw time. A real `MaterialHandle` is deferred to Phase 4, where it becomes an SRB and actually means something — introducing a pool wrapper around a plain struct now would be ceremony. Its `_uvOffset`/`_uvScale`/`_alphaCutoff` fields were **removed** after 2.b: they were placeholders that were serialized but never reached the renderer, and dropping them also cleared the `_uvScale: {0, 0}` values out of saved assets, so they can be re-added later with correct defaults and no migration.
- **`configs/light`'s R3D enums were originally deferred to Phase 7 — that was reversed in 2.c**, which had to convert them (see the 2.c entry for why). Nothing outstanding here.

### Phase 2 decisions taken in 2.d (both are shape-of-`IRenderer` calls — don't undo them silently)

- **The renderer owns the offscreen scene target; the caller never hands it one.** `resizeSceneTarget(w, h)` establishes it, and `beginScene` renders into it when it exists and to the backbuffer when it doesn't — which is exactly `R3D_BeginEx`'s own documented "invalid target → screen" behaviour, so one entry point serves both the editor and the game. The alternative (caller supplies a `RenderTexture2D`) was rejected because a raylib FBO is something a Vulkan/D3D Diligent backend physically cannot render into. This matches spike 0.3: Diligent owns an `ITexture` and hands out something wrappable as a raylib `Texture2D`.
- **`beginSceneOverlay()`/`endSceneOverlay()` exist, and they are GL-family-only by nature.** They make the rendered scene the active raylib draw target so the editor's grid and gizmos draw on top of it *with the scene's depth buffer still bound*. See the depth finding below for why this is not optional. They are editor-only (the game never calls them) and the editor is an OpenGL-backend process by the Phase 0.3 decision, so this is implementable for Diligent too — but a Vulkan/D3D backend must be free to no-op them, and `viewportWindow`'s gizmo/grid pass would then need Phase 8's "overlay after the blit" treatment instead.

**2.d verification, and the depth trap it exposed.** Screenshot-compared against the 2.c capture on the same Capsule + directional-light scene, and the game run separately.
- ⚠️ **Handing the scene to the editor as a colour texture silently drops the depth buffer.** The first attempt (renderer blits its scene texture into an editor-owned raylib canvas, editor then draws grid/gizmos into that canvas) built and ran fine, but the screenshot showed grid lines drawn straight *through* the capsule — the overlay had nothing to depth-test against, because only colour had been copied. Before the seam this worked by accident of colocation: r3d wrote colour **and depth** into the very render texture the editor then drew into. Fixed with the overlay brackets above. **This is a permanent property of the architecture, not an r3d quirk** — any design that moves the scene between the renderer and an rlgl overlay as a texture has it, so Phase 8 must either keep the overlay brackets or move the grid into the renderer as real scene geometry (the cleaner long-term answer, since a grid is scene content and gizmos legitimately want to draw on top).
- A second, smaller trap from the same attempt: the target is an FBO texture, so it needs exactly one vertical flip on its way to the screen. Two chained blits (scene → canvas → panel) each flipping cancelled out and rendered the viewport upside down. With the overlay design there is only one blit and one flip, which is what `drawSceneTexture` does.

**`example_game` was rendering nothing at all, and that had two independent causes** (fixing it was approved as part of 2.d, so this is a deliberate behaviour change, not a refactor):
1. `main.cpp` called `engine.onFrameEnd()` but never `engine.onFrameStart()`, so no `StartFrame` system ever ran — that is where `MeshRendererSystem`/`SpriteRendererSystem` issue their draws and where `GlobalLightSystem` applies the environment.
2. Deeper: `Engine::initializeSystems()` was only ever called from `Editor::initialize()`, so the standalone game had **no systems registered whatsoever**. Fixing (1) alone changed nothing; the game only started rendering its scene once `main.cpp` also called `initializeSystems()`.
Verified by screenshot: the game now renders the scene's capsule, lit, where it previously showed a bare environment-coloured screen.

**The game's own 2D and immediate-mode 3D are knowingly left broken — they get rebuilt on Diligent, not repaired on r3d.** In `example_game`, `Game_Render2DStart`'s text and `DrawFPS` are drawn *before* the scene pass and the scene render overwrites the whole backbuffer, so none of that 2D is ever visible; `Game_Render3DStart`'s `DrawCube`/`DrawCubeWires` are raylib immediate-mode calls with no `BeginMode3D` around them and don't render meaningfully either. Both are pre-existing and unchanged by 2.d. Fixing them against r3d would be throwaway work, because **the shipped game loses raylib/rlgl entirely at Phase 9** — see the new gap recorded there.

**Behaviour changes made knowingly in 2.c** (both fix leaks the old code had):

**Serialization risk from the original plan — RESOLVED, and the reason generalizes.** The plan flagged `INSPECT_FIELD(lightType)` on a raw `R3D_LightType` as a real migration risk for existing scene files. Verified in `inspectorObject.h`: enums are serialized as their **declaration index** via `magic_enum::enum_index` ([inspectorObject.h:616](modules/engine/inspectorObject.h)) and read back with `magic_enum::enum_cast` from that index ([inspectorObject.h:623](modules/engine/inspectorObject.h)) — **not** by name and **not** by underlying value; `inspectorObject.cpp:192` emits it as a bare int. So swapping `R3D_LightType` for `BreadEngine::LightType` needs **no scene migration at all**, as long as the new enum keeps the old declaration order. `LightType` is therefore locked to `Directional, Spot, Omni` (matching `R3D_LIGHT_DIR, R3D_LIGHT_SPOT, R3D_LIGHT_OMNI`) and `renderTypes.h` carries a do-not-reorder comment saying why. **Apply the same rule to every remaining R3D enum swap** (the `configs/light` ones in Phase 7, `R3D_CubemapLayout`, `TextureWrap`/`TextureFilter` in 2.b): keep declaration order, and no migration is needed. **2.b verification and the three real bugs it exposed.** Verified by running the editor on a scene with a Capsule primitive, the `scene.gltf` model (46 meshes / 2 materials / albedo+normal+ORM 4096² textures) and a directional light, with temporary `TraceLog` probes in the backend, then by screenshot. Two crashes/regressions only showed up at runtime — "it compiles" and even "it launches" would have missed both:
- **`R3D_LoadTextureFromImageEx` takes ownership of the image's pixel data.** Calling `UnloadImage` after it is a double free and segfaults on the first textured draw. This is undocumented in `r3d_texture.h` and is the reason the pre-seam `TextureAsset` never unloaded `_nativeRawImage` — what looked like a leak was load-bearing. The backend now clears the `Image` handle after handing it over and only unloads an image that was decoded but never uploaded.
- **Primitive mesh renderers were being destroyed and never rebuilt.** `MeshRendererSystem` unloads and reloads whenever `isChangedFromEditor` is set (it is, right after deserialization), but `loadModel()` only ever rebuilt the *mesh-asset* branch — a generated primitive was unloaded and gone. This was invisible before the seam because `MeshRenderer::unload()` left `_nativeMesh` non-zeroed after `R3D_UnloadMesh`, so `R3D_IsMeshValid` kept returning true and r3d kept drawing a freed mesh. Zeroing the handle (which a handle-based design does by construction) turned the latent UB into a visible disappearing capsule. Fixed by renaming `loadModel()` → `load()` and having it rebuild from `_meshPrimitiveData` when there is no mesh asset.
- **`auto &data = SpherePrimitiveData().asHalf();`** bound a reference to a destroyed temporary (`asHalf()`/`asQuad()` return `*this`) in both `meshRenderer.cpp` and `сreatePrimitiveCommand.cpp`. Fixed while rewriting those lines.
Also hardened: `setModelMaterial` bounds-checks the slot against the model's real `materialCount`, where the old loop trusted `_materials.size()`.

**Known issues deliberately left as-is in 2.b**:

Self-healing (the next `getData()` re-creates the handle) but it means a redundant decode+upload. Pre-existing; the right fix is refcounting in `TextureAsset`, not in the seam.

**Known issues deliberately left as-is in 2.a** (pre-existing, not introduced by the seam — fixing them would be a behavior change inside what is meant to be a pure refactor):

**Real build-system gotchas hit and fixed (not hypothetical, all order/global-scope issues — worth remembering since they can resurface if CMakeLists.txt structure moves around later)**:
- **Global `include_directories()` was actively dangerous once a third-party tree with generically-named headers entered the build.** Root `CMakeLists.txt` had a blanket (non-target-scoped) `include_directories()` listing `lib/engine/assimp` among others. Assimp ships its own generic `texture.h`; because that path came before DiligentCore's own include dirs on every subsequently-added target's command line (`include_directories()` leaks into every `add_subdirectory()` after it, including vendored third-party ones that never asked for it), DiligentCore's `#include "Texture.h"` resolved to **assimp's** `texture.h` instead of its own (Windows include paths are case-insensitive), breaking `EngineFactoryBase.cpp` with a bogus "undeclared identifier `TextureDesc`" error. Fixed by deleting the blanket block entirely — every path in it was already redundant with an existing `target_include_directories()` in `modules/engine/CMakeLists.txt` (PUBLIC, so it propagates to `BreadEditor`/`ExampleGame` via linking `BreadEngine`) or `modules/editor/CMakeLists.txt`. **Lesson: never use bare `include_directories()` in this project going forward** — always `target_include_directories()`, scoped to the target that actually needs it.
- **This project's own code had a latent, identically-shaped bug**: `modules/engine/models/reservedFileNames.h` and `modules/editor/models/reservedFileNames.h` are two different classes with the same filename. `modules/engine/configs/assets/file.h` included it as a bare `"models/reservedFileNames.h"`, which is fine when compiled as part of `BreadEngine` (whose own include order never sees the editor's copy) but broke once compiled as part of `BreadEditor`'s translation units (which put `modules/editor` before `modules/engine` on the command line) transitively via `assetsConfig.h` — resolved to the wrong (editor's) class. This was silently relying on the old blanket `include_directories()`'s ordering to paper over it. Fixed by making `file.h`'s include explicit/relative (`"../../models/reservedFileNames.h"`), matching the explicit-relative-path style already used elsewhere in this codebase for exactly this reason (e.g. `renameAssetCommand.h`'s `"../../../engine/configs/assets/assetsConfig.h"`). No other ambiguous same-name-header usage found (`cameraSystem.h` also exists in both trees, but every usage resolves via the "check the including file's own directory first" quote-include rule, so it was never actually ambiguous).
- **DiligentTools vendors its own zlib** (`ThirdParty/zlib`, for `TextureLoader`'s PNG support) which collided with `cpptrace`'s bundled `libdwarf` (FetchContent'd in `modules/engine/CMakeLists.txt`): `libdwarf`'s own bare `find_package(ZLIB)` (no `REQUIRED`) would pick up DiligentTools' local, non-exported zlib target instead of finding nothing (as it always had before Diligent existed in this tree). This showed up two different ways depending on CMake version: with system CMake 3.30, `libdwarf`'s `export(EXPORT libdwarfTargets ...)` failed at generate time (the picked-up target isn't part of any export set); with **CLion's bundled CMake 4.2** specifically, generate succeeded but the final executable link failed with `clang++: error: no such file or directory: 'ZLib'` (`ZLIB_LIBRARY` resolved to a bare, pathless token instead of a real path/target reference). Reordering `add_subdirectory()` calls alone was **not** a reliable fix across CMake versions — the actual fix is `set(CMAKE_DISABLE_FIND_PACKAGE_ZLIB ON)` immediately around `add_subdirectory(modules/engine)` (turned back `OFF` right after), which deterministically makes `libdwarf`'s `find_package(ZLIB)` report "not found" regardless of CMake version, restoring its pre-Diligent behavior. DiligentTools' own `libpng`→zlib linkage (which needs `find_package(ZLIB)` to succeed against its local vendored target) is unaffected since the disable is re-toggled off before DiligentTools is added. **Lesson: if this resurfaces, don't trust "it built once" as proof — verify with the exact CMake binary/version actually used to build (CLion bundles its own, separate from any system-wide `cmake`), since `find_package()`/target-resolution edge cases like this one are version-sensitive.**
- **DiligentCore always builds a `-shared` DLL variant alongside every `-static` target**, even though nothing needs them here. On this MinGW-w64/clang64 toolchain (`MINGW_BUILD` correctly auto-detected), the shared-lib link step passes `LINKER:--version-script=export.map` — a GNU-`ld`-only flag that this toolchain's linker (`lld`) rejects, breaking `GraphicsEngineVk`/`GraphicsEngineOpenGL`/`Archiver`/`SuperResolution`'s shared variants. Fixed by `set_target_properties(... EXCLUDE_FROM_ALL TRUE)` on those four targets right after `add_subdirectory(DiligentCore)`, since only the `-static` targets are ever linked against.
- **DiligentTools' standalone `HLSL2GLSLConverter` CLI tool doesn't build under MinGW/clang64** at all — it calls MSVC-only CRT debug-heap APIs (`_CrtSetDbgFlag`) that MinGW-w64's CRT doesn't provide. **Spike 0.3 results** (`spikes/diligent-poc/main_gl_interop.cpp`): tested whether Diligent's OpenGL backend can attach to raylib's already-created GL context and produce a texture raylib can blit directly (zero-copy), matching `viewportWindow.cpp`'s existing `R3D_SetResolution`/`DrawTexturePro` pattern.
- Confirmed `IEngineFactoryOpenGL::AttachToActiveGLContext` is the right call — but only when `EngineGLCreateInfo::Window.hWnd` is left **null**. A non-null handle routes Diligent's Win32 GL backend (`GLContextWindows.cpp`) through the "create our own context" path, which calls `SetPixelFormat` on the window's HDC — and Windows forbids setting a pixel format twice on the same HDC, so it throws (`Failed to set Pixel Format`) since raylib/GLFW already set one. With `hWnd` null, it takes the actual attach path (`wglGetCurrentContext()` + GLEW init against it), which worked immediately.
- Created a 256x256 `ITexture` (`BIND_RENDER_TARGET | BIND_SHADER_RESOURCE`), read its native GL handle via `ITexture::GetNativeHandle()` (returns the GL texture name directly, no need to `QueryInterface` for `ITextureGL`), and wrapped it as a raylib `Texture2D` by hand (`id`/`width`/`height`/`mipmaps`/`format` fields) — `DrawTexturePro` accepted it and rendered the Diligent-cleared texture correctly. Confirms the zero-copy path `viewportWindow.cpp` will need works.
- **Real gotcha found (not hypothetical)**: after Diligent's `SetRenderTargets`+`ClearRenderTarget` bind its own FBO on the shared context, raylib's rlgl has no idea the framebuffer binding changed underneath it — the first attempt produced a fully black window with raylib's draws silently landing inside Diligent's 256x256 offscreen texture instead of the real backbuffer (confirmed by screenshot: a black frame with only a ~256x256 correctly-rendered patch in the corner, sized exactly like the RT). Fixed by explicitly calling `pContext->SetRenderTargets(0, nullptr, nullptr, ...)` + `pContext->InvalidateState()` + `pContext->Flush()` **before** returning control to raylib each frame. **Carry this into Phase 8**: any code that lets raylib and Diligent share a GL context must bracket Diligent's rendering with this unbind/invalidate/flush sequence, or raylib's subsequent draws will silently go to the wrong target.
- Verified visually via screenshot (`gl_interop_result.png`), not just "didn't crash" — confirmed the orange Diligent-rendered square actually composites correctly into the raylib-drawn frame at the expected screen position.

**Spike 0.4 results** (read-only source inspection of `spikes/diligent-poc/DiligentFX/PBR/`, no build needed for this one): DiligentFX splits PBR support into two layers, and this split matters a lot for how much of Phase 4/5 can lean on it:
- `PBR_Renderer` (`PBR/interface/PBR_Renderer.hpp`) is the actual format-agnostic PBR pipeline: PSO management (`GetPSO`/`CreatePSO` returning raw `IPipelineState*`), a generic vertex attribute layout (`VERTEX_ATTRIB_ID_POSITION/NORMAL/TEXCOORD0/TEXCOORD1/JOINTS/WEIGHTS/COLOR/TANGENT`), and a generic material texture slot layout (`TEXTURE_ATTRIB_ID_BASE_COLOR/NORMAL/METALLIC/ROUGHNESS/OCCLUSION/EMISSIVE` plus clear-coat/sheen/anisotropy/iridescence/transmission for later). None of this requires glTF loading — it operates on `IPipelineState`/`IShaderResourceBinding`/vertex-buffer level.
- `GLTF_PBR_Renderer` (`public GLTF_PBR_Renderer : public PBR_Renderer`) adds a convenience layer on top whose `Render()` entry point takes a `GLTF::Model&`/`GLTF::ModelTransforms` directly — this part **is** glTF-specific and not reusable without adopting glTF's scene-graph loading conventions.
- **Decision**: drive `PBR_Renderer` directly with BreadEngine's own mesh/material data (matching its vertex/texture attribute IDs, since `meshAsset`'s existing texture-slot auto-wiring already approximates the glTF metallic-roughness convention per the original migration plan) rather than adopting `GLTF::Model`/`GLTF_PBR_Renderer::Render()`. Use `GLTF_PBR_Renderer`'s implementation only as a reference for how it drives the base class (PSO selection logic, resource binding order), not as a dependency. This de-risks Phase 4/5: BreadEngine's asset pipeline does not need to be reshaped around glTF's loader to get DiligentFX's PBR shading.
