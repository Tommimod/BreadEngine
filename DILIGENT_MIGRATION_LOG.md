# Migration log: r3d → DiligentEngine

Record of how each completed phase actually went — what landed, what broke, how it was found, what was verified against what. **This is history, not instructions.** Read the section for an area before working in it; do not read it end to end.

The working document — current status, the rules that must not be broken, and what is still planned — is [DILIGENT_MIGRATION.md](DILIGENT_MIGRATION.md). Anything in here that must not be re-broken belongs in that file's Invariants section; if you find something here that is load-bearing and missing there, move it.

### Between 6.c and 6.d — raylib 5.5 → 6.0, and the context to OpenGL 4.3

**Started as a blocker found while designing 6.d, and ended as the Phase 7 decision being taken early.** The plan's 6.d entry specifies `RESOURCE_DIM_TEX_CUBE_ARRAY`. Three facts, read in order, showed that was unreachable on the context we had:

1. `RenderDeviceGLImpl.cpp:919` — `CubemapArraysSupported = IsGL43OrAbove || CheckExtension("GL_ARB_texture_cube_map_array")`.
2. `HLSL2GLSLConverterImpl.cpp:575` — `TextureCubeArray.SampleCmp` converts to `texture(samplerCubeArrayShadow, …)`, which is GLSL 400.
3. `RenderDeviceGLImpl.cpp:364` — `MaxShaderVersion.GLSL = APIVersion`, so a 3.3 context emits `#version 330 core`; and `GLSLUtils.cpp:284` appends `#extension` lines **only when `IsES`**.

So even on a driver exposing the ARB extension — this machine's does — the shader could not have compiled, because nothing would have enabled it. There is a `ShaderCreateInfo::GLSLExtensions` field (`Shader.h:580`) that injects directives right after the version line, which would have made it work here and nowhere guaranteed. Four ways forward were written up for the project owner: that extension plus a runtime `CubemapArraysSupported` gate compiling the omni path out; a 2D array of six slices per light with analytic face selection; N separate non-array `TextureCube`s; or moving raylib to 4.3. **The owner chose 4.3 before the question was asked**, on the grounds that Phase 7 needs it anyway — and additionally asked that omni shadows be re-planned as their own step after it, rather than bundled in.

**What was actually done.** raylib tag `6.0` cloned into a scratch directory in the repo root, configured `-DBUILD_SHARED_LIBS=ON -DBUILD_EXAMPLES=OFF -DOPENGL_VERSION=4.3` with the project's own clang64, four headers and the DLL copied into `lib/engine/`, scratch directory deleted. No submodule, at the owner's request — the shape of `lib/engine/` is unchanged. `LibraryConfigurations.cmake:199` is what turns `OPENGL_VERSION=4.3` into `GRAPHICS_API_OPENGL_43`, and the configure output prints the resulting `GRAPHICS=` so it can be confirmed rather than assumed.

**Four checks made before the swap, and each of them saved work.**

- **The import table.** `llvm-objdump -p` on old and new DLL: byte-for-byte the same fifteen imports — five Win32 libraries and the UCRT stubs. A DLL built with a different toolchain would have dragged a second C runtime in, and that would have surfaced as a load failure rather than a link error.
- **The public API diff.** `RLAPI` declarations, 581 → 600, with eleven changed: seven `Text*` helpers, `DrawModelPoints`/`Ex`, `UnloadModelAnimation`, `UpdateModelAnimationBones`, plus three in rlgl (`rlCompileShader`, `rlLoadShaderCode`, `rlLoadComputeShaderProgram`, renamed per the changelog's `-WARNING-` entry). **None is used anywhere in `modules/`, `games/` or `lib/editor/`** — raygui's `TextSplit` is its own static, not raylib's.
- **`rlgl.h` under `_33` versus `_43`.** The public header is lines 1–818 and every `GRAPHICS_API_OPENGL_43` reference in it is version-selection plumbing; all real branches are past the `RLGL_IMPLEMENTATION` guard. So **no compile definition had to be added to any target** — which was the thing most likely to be got wrong, since a mismatched define between DLL and consumer is exactly the kind of failure that shows up as corruption much later.
- **The changelog, for the interop's own assumptions.** One entry mattered: rlgl's default clip range moved from 0.01/1000 to 0.05/4000. It cost nothing, because both sites that need it call `rlGetCullDistanceNear/Far`. That is now stated as a rule in Invariants rather than left as luck.

**The only code change in the whole swap was one comment** — `SHADOW_DISTANCE`'s, which asserted the camera's far plane was "a thousand units". It now names rlgl as the source instead of a number, which is true under both versions.

**What this releases downstream.** Cube map arrays for 6.d; `bitfieldReverse` for Phase 7's BRDF LUT; compute shaders and SSBOs for the compute-based PostFX components. The GLSL the engine's own shaders compile as went from `#version 330 core` to `#version 430 core` as a side effect — Diligent derives it from the context, so no shader source changed.

### Phase 6 — every light type, and two kinds of shadow

Split into three, because each part could be seen working before the next was written: **6.a** multi-light forward shading, **6.b** directional cascades, **6.c** spot shadow maps. Four decisions went to the project owner before any code, and all four took the recommendation — spot shadows in scope and omni out, a fixed-size cbuffer array rather than per-draw culling, `castShadows` without a matching `receiveShadows`, and varying PCF driven by the existing `shadowSoftness` field rather than a fixed 3×3 kernel. A fifth came up mid-phase and is in Invariants: `drawMesh` became `drawMesh(const MeshDrawDesc &)`, chosen over a sixth positional argument.

**Two API facts were checked before anything was written, and both changed the design.** Our HLSL reaches GL through `HLSL2GLSLConverterImpl` (`GLSLUtils.cpp:362`), not DXC — and that converter's own header says never to pass structs to functions, which `Shadows.fxh` does nine times with a struct full of matrices. It works, because none of those functions multiplies by one; only the call site does. And `PCF.fxh` already has a GL branch, but it is gated on `GL_SUPPORTED`, which nothing defines for us — an undefined macro is zero, so the default would have been the branch emitting `Texture2DArray.SampleCmpLevelZero`, the one function the converter documents as having no GLSL counterpart. Both are now in Invariants.

**6.a — the light array.** `SceneLight` is four `float4`s and nothing else, for the same reason `SceneFrameConstants` is: only `float4` and `float4x4` place identically in std140 and in C++. Everything the pixel shader would otherwise derive per pixel is folded in on the CPU — `1/range²`, the cosine of the half-angle, the reciprocal of the cosine span the cone's falloff covers. The array length is a shader macro rather than a number repeated in two places. Attenuation is the windowed inverse square (`saturate(1 - (d²/r²)²)²/d²`), which differs slightly from `PBR_Shading.fxh`'s unsquared window; the squared form is smoother at the range boundary and was kept deliberately. `Light` gained `spotAngle` and `spotBlend`, and `range` and both new fields are now conditional in the inspector on the light's type, since each is dead for the other types.

Selection past `MAX_SCENE_LIGHTS` sorts directional first then by distance-minus-range — and skips the sort entirely below the limit, because that is the only case where the order decides anything.

**6.b — cascades, and the convention problem underneath them.** `ShadowMapManager` in `SHADOW_MODE_PCF` allocates nothing but the depth array and its views, so the `IRenderStateCache` its other modes need for their conversion pipelines can be null. The real work was matrices. Diligent's camera space runs +Z forward — `GetFrustumMinimumBoundingSphere` returns `(0, 0, +FarPlane)` and `GetNearFarClipPlanes` reads a left-handed projection — where the engine's runs −Z, so `DistributeCascades` gets a left-handed basis and a `float4x4::Projection` built for it rather than the engine's own view matrix. The pixel shader's camera-space depth then comes from `dot(worldPos - cameraPos, cameraForward)`, which needs no view matrix and no handedness at all.

The other half is `PackMatrixRowMajor`, which defaults to *false* and transposes on the way out. Set **true**, DiligentFX's matrices land in exactly the layout `MatrixToFloatV` produces, and the whole shader stays `mul(matrix, vector)` with one convention. Worth stating plainly because it is not obvious: Diligent is row-vector with row-major storage, raylib is column-vector with `MatrixToFloatV`'s ordering, and the two transposes cancel — the same sixteen floats mean the same transform to both. What does *not* cancel is `memcpy` between a raylib `Matrix` and a float array: the struct declares its fields row by row while `MatrixToFloatV` emits them in index order. That was caught by reading `raymath.h` rather than by a wrong picture, and `renderShadowCasters` takes a `float16` specifically so neither caller can make the mistake.

Two smaller choices in the depth pass: `CULL_MODE_NONE`, because which winding faces the light depends on the handedness of the light's own view basis and a depth-only pass is cheap enough not to care; and `DepthClipEnable = False`, so a caster in front of a cascade's near plane is clamped rather than clipped away. `SHADOW_DISTANCE` caps the cascade fit at 60 units through the `AdjustCascadeRange` callback — the camera's far plane is a thousand, and fitting to that would spend the entire shadow map on distance nothing is shadowed at. And `shadowSoftness` maps to `fFilterWorldSize` through a 0.05 scale, because DiligentFX *grows the cascade* until the filter fits in 9×9 texels: a softness expressed in whole world units silently trades away most of the resolution.

**6.c — spot shadows, and why they are a second mechanism rather than the same one.** A spot needs one perspective map, not a set fitted to the camera's frustum, so `ShadowMapManager` has nothing to offer it. Four slices of a hand-built `Texture2DArray`, each rendered through `MatrixLookAt` × `MatrixPerspective` at the cone's own full angle — a cone is inscribed exactly in a square frustum of the same angle — and sampled with `FilterShadowMapVaryingPCF` directly. The two kinds travel separately through the light array on purpose: `Attenuation.w` says the cascades were fitted to this light, `Shadow.x` names a slice or is −1.

The one thing that shaped `scene.psh`'s structure: both shadow kinds need screen-space derivatives for their depth bias, and those are only defined where control flow is uniform across a quad. The per-light loop branches per pixel. So every shadow map is resolved *before* the loop — the cascades once, the spot slices in a fixed loop over `MAX_SPOT_SHADOWS` whose only branch is on a constant-buffer count — and the light loop just indexes the results.

**Verified by measurement, and one gap.** All of 6.a and 6.b were checked by sampling pixels rather than by reading a screenshot. A floor scanline through a white spot and an orange point light shows each light's own colour at its peak (`191,133,115` — R≫G≫B for the authored orange), a monotonic decay outward, a bend back toward neutral where the two overlap, and a floor of exactly `(80,80,90)` beyond them — which is precisely ambient-only, since `(20/255)^(1/2.2)·255 = 80` and `26 → 90`. That the range window closes to *exactly* the ambient value, rather than merely dimming, is what distinguishes a working attenuation from a plausible one. The directional shadow was checked the same way: shadowed floor at that same `(80,80,90)`, lit floor uniform at `151` across eleven samples with no acne, and a penumbra spanning several pixels rather than stepping in one.

**6.c was not seen in the session that wrote it** — the machine was in use and the editor window was closed within seconds on each of four attempts, so it was recorded as unverified rather than quietly counted as done. It was verified in the next session, after the three defects below were fixed.

#### Three defects found by the project owner in the editor, and what each one teaches

All three were invisible at build time, and the first one is the reason this pair of files insists that "it compiles" proves nothing.

**A random crash while rotating the camera — and the camera had nothing to do with it.** The shadow constant buffer was created with `Size = sizeof(ShadowMapAttribs)` in 6.b, and 6.c then grew the struct written into it by four matrices and four vectors without touching the buffer. Every frame wrote 320 bytes past the end of a mapped driver allocation. The symptom was a process that died at unpredictable moments, with a clean log and an empty stderr; the reported trigger was looking at the sky, which was pure coincidence — memory corruption surfaces wherever the corrupted allocation is next used. It was found by reading the two declarations side by side rather than by reproducing, and `uploadConstants` now refuses any write larger than `GetDesc().Size` and logs it, so the whole class is loud from here on.

**The spot near plane was derived from the light's range.** `nearPlane = max(range * 0.01, 0.05)` looked defensible when every test light had a range of 20. The owner's test light had `range = 5000`, which put the near plane at 50 units — past every caster in the scene. And because the shadow pipeline sets `DepthClipEnable = False` (so a caster in front of the near plane is kept rather than clipped), those casters were clamped to the nearest depth instead of disappearing, which made them occlude everything. The symptom on screen is worth remembering because it does not look like a near-plane problem at all: **a lit object whose brightest, most directly-lit areas are dark while the edges of the cone are lit.** The fix is a constant near plane; `range` is how far a light reaches, and reach has no business setting depth-buffer bounds. A float depth buffer spends its precision near the eye, so a small constant costs nothing where casters actually are.

**The spot PCF kernel had no ceiling.** `shadowSoftness` maps to texels for a spot, and the owner's light had softness 5 → a 15×15 kernel, 225 taps per pixel. The cascade path cannot hit this because DiligentFX *grows the cascade* until the filter fits in 9×9; nothing does that for a fixed projection, so the spot filter is now clamped to the same 9 texels the varying filter is written for.

**How 6.c was finally verified, and why the method is better than the obvious one.** Under a warm sun plus a white spot, a horizontal profile across the cone reads: `230,228,220` outside it (R > B, warm — sun only), `255,255,255` inside it, and `214,216,220` inside it but behind the capsule (B > R, **cool**). The hue flip is the proof: measuring only brightness would show that something got darker, which any bug could produce, while the channel order shows that specifically the white light was removed and the warm one was not. The penumbra spans ~150 px of gradient, consistent with the clamped 9-texel filter.

#### A bug-hunt pass over the render path, after 6.c

Asked for by the project owner, starting from one symptom they remembered: a light kept shining after its node was set inactive. It turned out to be one of three faces of a single root, and **the root is worth stating on its own: a light is the only render resource whose state the renderer keeps between frames.** Meshes, materials and sprites are re-submitted every frame, so skipping an inactive node stops them drawing. A light is retained, so skipping it leaves the last value applied.

**The first fix was wrong, and checking the assumption is what caught it.** The obvious change was to stop `LightSystem::update` returning early on an inactive node and have it push `active = false` instead. That does nothing: `SystemsRegistry::update` line 19 is `if (!node->getIsActive()) continue;` — the runner skips inactive nodes before any update system sees them, so the internal check could never run. `startFrame` and `endFrame` have no such filter, which is exactly why `MeshRendererSystem` carries its own. The real fix is `LightSystem` becoming a start-frame system, which also removes a rounding error nobody had noticed: lights read transforms in `update` while meshes read them in `startFrame`, one phase apart.

**`destroyLight` had no caller anywhere in the engine.** `Light` was the one handle-owning component without an `onDestroy` override, while `ComponentChunk::remove` calls `onDestroy()` and then overwrites the slot with `T{}`. So deleting a light node dropped the handle on the floor and left the pool entry alive with `active = true` — permanently lit, unreachable, and the pool grew without bound. This is a straight violation of an invariant that was already written down, which is worth noting: the rule existed and the component still shipped without it.

**The camera looked like the same bug and needed the opposite fix.** `CameraSystem` is an update system too, so deactivating a camera node freezes `_nativeCamera` rather than disabling it, and `getActiveCamera()` handed it out regardless — the scene kept rendering from wherever the camera stood when it was switched off. The tempting move was to repeat the light fix and make it a start-frame system. Checking the frame order first showed that would be a regression: `ExampleGame` runs `update` (main.cpp:30) before `beginScene` (39), while the editor runs `beginScene` (88) before `update` (91). The camera is consumed at the *top* of the frame where lights and draws are consumed at the *bottom*, so start-frame would make it lag a frame in both hosts. The fix went into `CameraDirector::getActiveCamera()`, which now returns null for a camera on an inactive node; both callers already handle null, and `ExampleGame` uses its own `Camera3D` rather than the component at all.

**Copy and move operations, where the move half was the dangerous one.** The stated goal was to pre-empt a future duplicate-node command, which would have given two nodes one handle. But reading `ComponentChunk` first turned up something already live: it grows with `_components.resize(capacity * 2, T{})`, and a vector relocates through `move_if_noexcept` — while every component declares `~T() override = default`, and a user-declared destructor suppresses the implicit moves. **The chunk was therefore already relocating by copy**, and it only worked because the destructors released nothing, so the old objects died silently and the copies inherited the same handles. Adding a copy constructor that drops GPU state — which is exactly what was being asked for — would have turned that accident into the loss of every live handle the moment a chunk grew.

So all three handle-owning components (`Light`, `MeshRenderer`, `SpriteRenderer`) got both halves: a copy that carries authored data and drops GPU state, per the contract `Material` set in Phase 4, and a `noexcept` move that transfers it. `static_assert(std::is_nothrow_move_constructible_v<T>)` on each makes the requirement a compile error rather than a comment, because the symptom of breaking it looks nothing like the cause. `MeshRenderer::unload` and `SpriteRenderer::unload` were guarded with `Renderer::isAlive()` along the way — previously unguarded, and inside a `noexcept` move assignment a throw is `std::terminate`.

**Verified**: the light was confirmed extinguished by deactivating the owner's test light and diffing the floor profile — the cone vanishes entirely, and where it was the floor reads either the warm sun-lit value or `86,92,101`, which is ambient-only, i.e. the capsule's *sun* shadow that the spot had been washing out. After the lifetime changes the frame is pixel-identical to before them: total channel delta 0 across 21 samples. Two smaller findings were recorded rather than fixed, both flagged to the owner: only the first shadow-casting directional light gets cascades and the rest are silently unshadowed, and on reactivating a camera node the editor shows one stale frame because `beginScene` precedes `update` there.

#### The test scene gained a floor, and its lighting stopped hiding the shadows

Asked for once the shadows worked: on the checked-in scene no shadow was visible anywhere, and there were two independent reasons. There was **no receiver** — the scene was three objects over an rlgl grid, and the grid is an overlay that never passes through `drawMesh`. And even self-shadowing was invisible for a reason worth stating as arithmetic rather than as taste: the ambient term is `ambientColor · energy · albedo`, the background was white at energy 1, so ambient alone already reached 1.0 on any light surface. The directional term was added on top and clipped; removing it in shadow changed nothing at all.

So the scene now has a 40×40 Floor plane with `castShadows: false`, the capsule moved to `y = 1.48` to rest on it, a dim blue-grey background `(66, 78, 96)`, `_ambient.energy` at `0.35`, and a warm sun at intensity 3 tilted off vertical. Measured afterwards: shadowed floor `(86, 92, 101)`, lit floor `(230, 228, 220)`. The trap while authoring this: **the ambient colour cannot be set in `global_light_settings.cnf`** — `GlobalLightSystem` overwrites it from the active camera's background every frame while the mode is `SOLID_COLOR`. `energy` is the only ambient field that survives, and the camera's `_backgroundColor` is the real control.

### Between phases — materials became project assets

Not a phase: a detour requested by the project owner after Phase 5, before Phase 6 started. A `Material` was a procedural value copied into every `MeshRenderer` and `SpriteRenderer`, so the same surface authored twice was two unrelated sets of fields. It is now an asset in the project tree.

**Four decisions were put up before any code was written**, with the inspector's own limits measured first, because two of the options were only cheap or only expensive depending on them:

1. **The component holds a per-slot struct, not a raw `MaterialAsset *`.** This one was not offered as a choice — it is a cost fact. `std::vector<MaterialAsset *>` cannot round-trip through the existing inspector: `TypedVectorAccessor::get/set` `any_cast` the exact pointer type while the asset machinery deals in `Asset *`, `propertyToYaml`'s `VECTOR_L` switch has no `ASSET_LINK` case, and `setPropertyByPath` cannot route a deferred link into `_materials[2]`. A vector of *structs each holding* a link needs none of that — it is exactly what `_materials[0]._albedoTexture` already did. `MaterialLink` is that struct, and it is also the only place a future per-renderer instance flag can live.
2. **`MeshAsset` drops materials entirely** rather than keeping its auto-wired ones as a fallback or extracting a `.mat` per model material on import. `wireTextures`, `findTexture`, `findConventionalTexture`, the importer's `ModelMaterial`, and `MeshAsset::loadToMemory`'s import-just-to-count-materials all went with it; `MeshAsset` is now geometry and a refcount. The accepted cost is that `scene.gltf` renders untextured until a `.mat` is linked to its slots.
3. **`SpriteRenderer` keeps both** its `TextureAsset` and a material link: the texture sizes the quad and builds the material drawn while nothing is linked, and a linked `.mat` overrides appearance. It cannot be reconciled further until instanced materials exist, because a shared material's texture set is fixed once created.
4. **Split by ownership**: `MaterialAsset` under `configs/assets/` with the other assets, `MaterialLink` in `data/` with the components that hold it. `data/material.{h,cpp}` was deleted.

**The storage decision was reversed on review, and that reversal is the interesting part.** The first implementation put the material's fields in `assets_registry.cnf` like a texture's settings, with the `.mat` as a marker file — chosen for costing no new save path at all, since `serializeConfig` already writes every asset. It worked and was verified. The owner rejected it on a ground the implementation had not weighed: **a registry-wide file makes a one-material change unreadable in a diff.** Moving the fields into the `.mat` needed the assets system to grow a real distinction — `Asset::isStoredInOwnFile()` and `saveToOwnFile()`, the encoder skipping self-stored assets, and `AssetsDeserializer` losing the material pass it had just gained. The rule that fell out of it is in Invariants: the two storage kinds are exclusive, because the registry's copy loads last and would win.

**The subtle one: a self-stored asset must load outside a deserialization phase.** `MaterialAsset::loadToMemory` resolves texture links through `InspectorStruct::deserialize`, which defers `ASSET_LINK`s while a phase is open — and `resolveAllDeferredAssetLinks` only delivers to components, so an asset's link would vanish with no error. Load order already satisfies it (`restoreEngineAssetsByFiles` runs after `AssetsDeserializer` closes its phase, and before any scene), and `loadToMemory` now logs a warning if that is ever untrue, so the failure cannot stay silent.

**Two smaller things that had to be right.** An unlinked slot must still produce a *valid* handle, because `endScene` skips a draw whose material does not resolve — so an unlinked mesh would have been invisible rather than untextured, which the "a loaded mesh always has a material" invariant exists to prevent; `Renderer::defaultMaterial()` is the process-wide one, cleared on shutdown so a re-initialized renderer does not name a dead slot. And `MeshRenderer::getMaterials()` now derives the list length from the parts' highest material slot instead of copying it from the asset, since there is no asset list to copy any more.

**Verified on screen, four ways**, against the test scene under both the editor and `ExampleGame`:

- The Cube and `scene.gltf`, both linked to one `.mat`, render with the same albedo/normal/ORM they had before the change — the whole chain, from the file through the registry's guid links to the draw.
- The Capsule, whose slot links nothing, was checked against a temporarily darkened camera background (white-on-white otherwise, per Phase 5's note): it draws lit and untextured, occluding the grid. That is `Renderer::defaultMaterial()` working.
- After the switch to file storage, the registry the editor writes on load contains **zero** material entries, and the `.mat` is byte-identical before and after — the load-time `serializeConfig` rewrite is a no-op on unchanged materials, so it produces no diff noise.
- A zero-byte `.mat` (what "Create Material" leaves on disk before the asset fills it in) loads as defaults and is written out complete, with no warning on either stream.

The scene under `games/example_game/assets/` was migrated by hand to match: `3D/scene.mat` holds the material, `Root.nd`'s slots link it by guid, and the stale `_materials` block under the model's registry entry is gone.

### Phase 5 — the six generators and the assimp importer

Both halves landed together because the second one decided the shape of the first: once the engine imports geometry itself, the renderer only ever receives `MeshData`, and generating a primitive is the same call as loading a model.

**Three decisions were put to the project owner before any code was written**, and all three took the recommendation:

1. **Model import moved in front of the seam.** `ModelHandle` and its four methods (`loadModel`, `destroyModel`, `getModelMaterialCount`, `setModelMaterial`, `drawModel`) are gone, replaced by one `createMesh(const MeshData &)`. `createPrimitive(MeshPrimitiveData, forward)` collapsed into it too, so the renderer no longer includes an inspector type and no longer knows what a primitive is — `generatePrimitive` is called by `MeshRenderer`/`SpriteRenderer` instead. Net: `IRenderer` lost five methods and gained one, and assimp is now reachable only from import-time code, which is what Phase 9 needs in order to drop it from the shipped runtime.
2. **"Cached mesh format" means in-memory for this phase.** `MeshAsset` imports once per run and drops the CPU-side geometry as soon as it is uploaded. A binary on-disk cache is deliberately deferred — the test scene has one model, so startup time is not yet measurable, and the format would need versioning against `MeshVertex`, which is a documented contract.
3. **`MeshAsset` owns the model's buffers, refcounted**, mirroring `TextureAsset` exactly: `acquire()`/`release()`, an empty import takes no reference, and two nodes on one model share one set of buffers.

**The importer flattens the hierarchy.** `appendNode` walks the scene accumulating each node's transform into the vertices beneath it, so a part is drawable with nothing but the renderer's object transform. Positions take the 4x4 (assimp's `matrix * vector` adds the translation column); normals take the inverse transpose of its 3x3 part, so a non-uniformly scaled node keeps its normals perpendicular. `aiProcess_PreTransformVertices` would have done the flattening in one flag and was passed over on purpose: it also strips bones and animations, which Phase 10 needs, and the explicit walk is the code that phase extends rather than replaces. Nothing in the flag set rewrites the coordinate system — assimp keeps the file's right-handed, counter-clockwise, v-down convention, which is already the engine's, and the model rendered with readable (un-mirrored) decal text on the first try.

**`MeshPart` is the unit both halves produce**: a `MeshHandle` plus the material slot it draws with, in `renderTypes.h` because the asset and the component both need it. A primitive is one part at slot 0; the test model is 46 parts over 2 slots. The draw loop clamps the slot with `std::min(materialSlot, lastSlot)` — not defensive padding, but required: the inspector can shorten the material list at any time without raising a flag, while the slot indices come from the source file.

**`MeshRenderer` keeps `_acquiredAsset` separate from `_meshAsset`.** Same trap Phase 4 paid for with textures: the inspector rewrites the asset-link field directly, so the field cannot be trusted to name the asset a reference was taken from. The field doubles as the discriminator for who owns the parts — non-null means borrowed from an asset and released, null means generated here and destroyed here.

**Verification, and two false alarms it produced.** The first full-scene screenshot showed the model rendering (its first appearance ever under Diligent — `loadModel` had been a stub since 3.6) but neither the Cube nor the Capsule, which read as a regression against the one thing 3.c had verified. Both were artefacts of the test scene, not the code:

- The **Capsule has no textures**, and the scene's ambient is white at energy 1 against a white background, so an untextured surface is white-on-white by construction. It is genuinely there — it shows up as the capsule-shaped gap it punches in the rlgl grid lines, which incidentally re-confirms the depth-shared overlay still works.
- The **Cube was behind the model**, which is several units long and sits over the origin from that camera. Deactivating the model node in the build-directory scene copy showed the cube rendering correctly at the origin.

**What actually settled it was numbers, not pixels.** Under flat white ambient there is no shading gradient, so a small cylinder is indistinguishable from a flat quad on screen at test-scene scale. Logging each generator's vertex/index counts and bounding box was decisive and cheap: cube `[-0.5,0.5]³`; sphere r=1 `[-1,1]³`; hemisphere `y ∈ [0,1]`; cylinder r=0.5 h=1 `[-0.5,0.5]³` with 2 wall rings × 31 + 2 caps × 32 = 126 vertices; capsule `y ∈ [-1.5,1.5]`, i.e. exactly `height + 2·radius`; plane flat in Y; quad flat in Z facing the node's forward. Sphere, hemisphere, capsule and quad silhouettes were also confirmed visually side by side.

**A trap in hand-writing test nodes into `Root.nd`:** six nodes given ids 100–105 crashed the game during scene load, before the first frame, with no message on either stream. The same six nodes with ids 10–15 loaded and ran fine. Whatever the engine does with node ids is not id-agnostic — worth knowing before authoring scene YAML by hand again, and worth a look if a scene ever fails to load for no visible reason.

#### Three defects found after Phase 5 landed, two of them pre-existing

Found by the project owner using the editor, which is where all three had to surface — none was reachable from the test scene.

**Primitives from the toolbar produced empty nodes.** `CreatePrimitiveCommand::applyData()` guards on `!node->has<MeshRenderer>()`, but its node comes from `CreateEmptyNodeCommand`, which makes a Transform-only node. Nothing ever added the component, so that guard bailed out on every call and the primitive was never built. The sibling `CreateLightCommand` does `node->add<Light>()` in its own `onNodeCreated`; the primitive command was simply missing the equivalent. Pre-existing, and invisible until now because a mesh that is never built looks the same as a mesh that fails to render.

**Adding that line exposed a null owner in `ComponentsProvider::addImpl`.** It never called `setOwner`, unlike all three `addDynamic` overloads, so `Node::add<T>()` returned a component whose `_owner` was null — and `MeshRenderer::createPrimitivePart` reaches its node's `Transform` through it. Everything loaded from a scene file goes through `addDynamic`, which is why this had never been hit: nothing had added a `_owner`-using component in code before. Fixed at the root, in `addImpl`, before `onCreate` so the ordering matches `addDynamic`.

**Imported UVs were vertically flipped**, which is not something to reason about from convention — `glTF2Importer.cpp` does `values[i].y = 1 - values[i].y` with the comment "Flip Y coords", because assimp's internal UV origin is the bottom-left while glTF's is the top-left. The engine samples top-left, so the fix is `aiProcess_FlipUVs`, which the vendored `postprocess.h` documents as producing exactly that origin. Reading the file first also ruled out the alternatives: one material, all 46 primitives on `TEXCOORD_0`, and no `extensionsUsed`, hence no `KHR_texture_transform` to honour.

Worth recording about the verification: **nothing built before this point actually tested the V orientation.** The cube maps 0..1 per face over an atlas, so a flip there produces arbitrary-but-plausible content on every face and reads as normal. It took a model with a real unwrap to expose it.

#### Materials now come from the model file

Asked for immediately after, and the natural completion of the phase: the importer already reads materials, so wiring textures by file name was leaving the file's own references on the floor. `ModelData::materialCount` became `ModelData::materials`, a `ModelMaterial` per slot holding the four declared paths — one source of truth instead of a count plus a separate convention. Each engine slot draws from an ordered list of assimp types, because the formats disagree: `BASE_COLOR` then `DIFFUSE` for albedo, and for the packed ORM slot `GLTF_METALLIC_ROUGHNESS`, `METALNESS`, `DIFFUSE_ROUGHNESS`, `LIGHTMAP` in that order. Embedded textures (reported as `*<index>`) are skipped — the asset pipeline resolves project files, and a GLB's images are not files.

The importer still touches no assets: it returns paths, and `MeshAsset` resolves them against the registry, normalising forward slashes to the separator the registry keys on. The convention survives as a per-slot fallback, deliberately, because the checked-in test model cannot exercise the new path at all: `scene.gltf` names `textures/lambert1_baseColor.jpeg`, and those files were renamed to `scene_albedo.jpeg` etc. to satisfy the old convention, so the declared paths resolve to nothing. Removing the fallback would have silently un-textured the test scene.

**Colour space was deliberately left out of this**, and the reasoning is in Invariants so it does not get re-proposed: the import could infer that a normal or ORM map is data and clear `_withColor` itself, and the project owner ruled against it — a `TextureAsset` is shared and its fields are serialized, so the import has no business writing settings on an asset the model does not own. Reading the registry while working on this turned up that the scene's normal and ORM maps both carry `_withColor: true`, so they are being gamma-decoded today; that is a scene-data fix for whoever wants it, not a shader bug to chase.

**Capsule `height` is the straight section, not the total.** The stored defaults settle it rather than taste: `height = 1, radius = 1` would be a negative-length shape under the total-height reading, so the serialized field can only ever have meant the cylindrical part.

### Phase 4 — `MaterialHandle` and texture refcounting

The two halves left after 3.c landed together because they are the same problem seen from both ends: a material that owns a binding must also own the texture references that binding was built from.

**What the API fact forced.** `SHADER_RESOURCE_VARIABLE_TYPE_MUTABLE` is documented in `ShaderResourceVariable.h` as set *once* and unchangeable after binding. So a material is exactly its SRB: `createMaterial(MaterialDesc)` builds one, fills its four texture variables, and never touches them again; changing a material's textures means creating another material. That is what makes `MaterialHandle` a real handle rather than a wrapper around the same four texture handles. The pipeline's material variables went DYNAMIC → MUTABLE, `bindMaterial` and the single `_sceneResources` binding are gone, and the draw loop now commits the material's own SRB. `MaterialData` became `MaterialDesc`, since it is now a creation descriptor like `TextureDesc` and not something a draw call carries.

**Ownership, decided by the project owner.** Two alternatives were put up — a renderer-side cache keyed by the texture set, and component-owned handles parallel to `MeshHandle` — and `Material` owning its own handle was chosen: explicit lifetime, matching the rest of the seam. The price is copy discipline in a serialized value type, paid as: **a copy of a `Material` carries the asset links and no GPU state**, so it resolves a material of its own on first use. Copy-assignment unloads the destination first. Copying is therefore always *correct*; at worst it costs a rebuild. There is deliberately no destructor — `Renderer::get()` throws outside the renderer's lifetime, so release stays explicit through `unload()`, as everywhere else in the engine.

**Invalidation is a comparison, not a flag.** `Material::getHandle()` rebuilds when the linked assets no longer resolve to what the material was built from. Nothing can be hung off the setters: the inspector writes `_albedoTexture` and friends directly through a member pointer, bypassing them entirely. The per-frame cost is the four `getTexture()` calls `getData()` already made.

**Refcounting.** `TextureAsset::unload()` became `acquire()`/`release()`; only the count reaching zero destroys the texture. `acquire()` does not count an invalid handle, so a load that never produced a texture cannot be released against. The assets registry's eager load of every project image at startup takes no reference, so an unused texture simply stays resident — the refcount governs sharing, not preloading.

**Two call sites moved as a consequence.** `MeshRenderer::unload()` used to return early on the primitive path and never unload its materials — harmless when a material owned nothing, a leak once it owns an SRB; both paths now fall through to the same material loop, and `setGeneratedMesh`'s duplicate loop went away. `SpriteRendererSystem` used to detect an inspector-assigned texture by comparing the material's baked albedo against the asset; the quad's *size* is what actually depends on that texture, so `SpriteRenderer` now records the handle it sized itself against (`_quadTexture`) and the material keeps no accessor for it.

#### Review pass after Phase 4 — six defects, two of them serious

Two reviewers were run over the finished diff, one for architecture and one for correctness. Everything below was found by reading, not by running; the frame was pixel-identical before and after the fixes (same 694 distinct colours, same centre pixel), which is the point — none of it was visible.

1. **A reference was given back to the wrong asset.** `unload()` paired the *current* `TextureAsset *` link with the *stored* handle. The inspector writes those link fields directly, so reassigning a material's albedo in the editor released the new asset's reference — dropping a texture another material was still using — while the old asset's reference was never returned and pinned it resident. Two materials sharing a texture then invalidated each other every frame, each rebuild re-decoding the file from disk and blocking the render thread. **The fix is the rule now in Invariants: a reference goes back to the asset it was taken from, so `Material` stores that pointer next to the handle** (`AcquiredTexture`), rather than trusting a link that can be rewritten underneath it.
2. **Nothing released a component's GPU resources when its node was deleted.** `MeshRendererSystem::onDispose` only runs at engine shutdown; a node deleted in the editor goes `Node::destroy` → `ComponentChunk::remove`, which calls `onDestroy()` and then resets the slot. Neither renderer component overrode `onDestroy()`, so every deleted node leaked its mesh — **a pre-existing leak that predates Phase 4 and would have quietly gained the material SRB and its texture references.** Both components now override it.
3. **`Material` had no destructor, and declaring the copy operations had suppressed the implicit moves.** The inspector's `+`/`-` buttons on a materials list reallocate and erase that vector, destroying live materials with no way to release anything. `Material` now has a destructor, guarded on `Renderer::isAlive()` — the new accessor exists because a shut-down renderer is the normal end of the process, and `get()` throwing out of a destructor is not survivable. Explicit `unload()` survives only as the force-a-rebuild path.
4. **A renderer that failed to build a material retried every frame**, releasing and re-acquiring the textures each time — a decode loop on top of an already-broken pipeline. `_isResolved` latches the attempt, so a failure costs one.
5. **The null check on `GetVariableByName` was dropped in the rewrite.** It returns null for a name the shader does not sample, and shaders are compiled from disk at runtime, so a shader edit that stopped sampling one slot would have segfaulted instead of logging. Restored.
6. **`unload()` had grown a material loop it did not need.** `MeshRendererSystem` calls it on every inspector change, so each edit was round-tripping the textures through disk. Materials invalidate themselves and release themselves, so `unload()` is geometry only again.

Two **pre-existing** crashes were found alongside these, both reachable from the editor and neither caused by this diff, and both were fixed on the project owner's call. They share a root: the inspector's list `+`/`-` buttons and its asset-link fields mutate a component's serialized state directly and **raise no `isChangedFromEditor`** (`UiInspector::track` only re-binds the panel), so nothing downstream is told to re-derive.

- `MeshRendererSystem` indexed `_materials[0]` unconditionally, and `-` can empty that vector. The rule the owner set is that a mesh always has a material — the one from its asset, or a default with empty texture slots — and renders untextured rather than not at all. `MeshRenderer::getMaterials()` now carries that guarantee and restores the default; `load()`'s copy of it was removed so there is one owner of the invariant, not two.
- `SpriteRendererSystem` dereferenced `_textureAsset` while `_isLoaded` was still true, which is what clearing a sprite's texture link leaves behind. The comparison moved onto the component as `isQuadStale()`, which treats a cleared link as stale; the system then re-checks `isLoaded()` after the reload, since a cleared link leaves nothing to build a quad from.

**Verified**: both targets build; editor and `ExampleGame` each render the test scene's textured lit cube with no Diligent errors logged. The regression this change could plausibly have caused is the fallback 1×1 white albedo binding instead of the real texture, which was ruled out by measurement rather than by looking: 4225 samples across the cube give 694 distinct colours, mean saturation 0.13, and a centre pixel of `(14, 77, 64)` — the scene texture, not a flat lit grey.

### Phase 3.5 — the `PBR_Renderer` spike, and why it was not adopted

Method: a throwaway TU in the Diligent backend, called from `initialize()` after the device attach, building four `PBR_Renderer` instances against the **live** GL 3.3 context and asking each for one PSO. Deleted once the decision landed. The point of running it inside the editor rather than in `spikes/` was that the context under test is exactly raylib's, not one a standalone harness negotiated.

**The feared blockers were not the real ones.** The plan expected `gl_DrawID` and structured buffers to sink it. Neither appears in the generated source unless asked for: `gl_DrawID` is only emitted when `CreateInfo::PrimitiveArraySize > 0` (`PBR_Renderer.cpp:1427`) and the structured joints buffer only when skinning is on. With `PrimitiveArraySize = 0`, `MaxJointCount = 0`, `OITLayerCount = 0`, **every PSO compiled on GL 3.3** — base, plus tone mapping, plus IBL, plus shadows.

**The one real failure is narrow and is not in the render path.** `PrecomputeBRDF.psh` fails to compile:

```
0(1596) : error C7532: global function bitfieldReverse requires "#version 400" or later
          ... or #extension GL_ARB_gpu_shader5 : enable
```

It is the one-time BRDF LUT pass, needed only for IBL. `PBR_Renderer::PrecomputeBRDF` is **private and non-virtual** (`PBR_Renderer.hpp:919`) and there is no setter for `m_pPreintegratedGGX_SRV`, so it cannot be substituted from outside — the fix would have to be a patch to the vendored submodule or GL 4.x. DiligentCore itself hits this and works around it by prepending a hand-written `bitfieldReverse` stub, but only in the Archiver's GLES path (`Archiver_GL.cpp:140`). Probe on this machine: RTX 2060 SUPER, `GL_ARB_gpu_shader5` **available** even in the 3.3 context — NVIDIA is liberal with ARB extensions there; Intel/AMD are not guaranteed to be.

Two secondary findings that moved the decision more than the compile result did:

- **`PBR_Renderer` does not dictate the vertex layout**, which is what the phase existed to protect Phase 5 from. `CreateInfo::InputLayout` is taken verbatim (`PBR_Renderer.cpp:1685`); only the attribute *indices* are fixed, and the only clash with `MeshVertex` is tangent at ATTRIB7 instead of ATTRIB3. Auto-offsets resolve in declaration order, so the buffer's byte layout would not have changed at all.
- **It does dictate the material binding, and that one costs serialized inspector fields.** Every material map is a `Texture2DArray` even in the simplest mode (`Shaders/PBR/private/PBR_Textures.fxh:183`), while `TextureLoader` hardcodes `RESOURCE_DIM_TEX_2D` (`TextureLoaderImpl.cpp:398`) — their own GLTF loader works around it by rebuilding the desc (`GLTFLoader.cpp:724`), five lines. Cheap. What is not cheap: samplers are **immutable and per texture *slot*, one set for the whole renderer** (`PBR_Renderer.cpp:1244`), so `TextureAsset::_textureFilter` would stop having any effect; and wrap, which survives because the shader applies it per material from `PackedProps`, explicitly **does not support Mirror** (`PBR_Textures.fxh:412`), so `MirrorRepeat`/`MirrorClamp` would have to be dropped from `TextureWrapMode`.

`Texture2DArray` itself was checked for a victim and has none today: the editor draws no texture previews (no `DrawTexture*` anywhere under `modules/editor`) and sprites go through `drawMesh` like meshes, so nothing in the tree needs a `GL_TEXTURE_2D` to hand to rlgl.

**Decision (project owner): keep the engine-owned shader, adopt DiligentFX component by component.** The library is not a monolith — `ShadowMapManager`, the `PostProcess/` effects, `ToneMapping`, `EnvMapRenderer`, `CoordinateGridRenderer` and the `Shaders/Common/public/*.fxh` includes are all reachable without `PBR_Renderer`, so refusing the renderer forfeits much less than refusing DiligentFX would. The per-phase list is in the plan under Phase 3.5; keep it there so it does not get re-argued.

### Phase 3 checklist

- [x] **3.a Backend skeleton.** `rendering/backends/diligent/diligentRenderer.{h,cpp}`. `AttachToActiveGLContext` with `Window.hWnd` left null (spike 0.3's finding), an offscreen colour+depth `ITexture` pair as the scene target, `beginScene` clearing to the environment's background colour, and `drawSceneTexture` blitting the colour texture's GL name as a raylib `Texture2D`. `modules/engine/CMakeLists.txt` links `Diligent-GraphicsEngineOpenGL-static` **and `Diligent-Common`** for the Diligent backend — `Diligent-Common` (which carries `RefCntAutoPtr`) is a *private* dependency of the GL engine target, so its include directory is not propagated by linking the engine target alone. **Verified**: `BreadEditor` builds 711/711 exit 0 in a second build directory, runs 22 s on the Capsule + directional-light scene with zero Diligent errors or warnings logged, and the viewport screenshot matches the R3D build's background colour, grid and camera framing exactly (only the capsule is missing, since draw is still a stub).

**Sub-phase 3.a decisions** (both are inside the backend — `IRenderer` is unchanged — but they are shape decisions, not details):

- **The editor's overlay pass draws into a raylib framebuffer built over Diligent's own two textures.** `rlLoadFramebuffer()` + `rlFramebufferAttach` on the colour and depth textures' GL names, so `beginSceneOverlay`'s `BeginTextureMode` puts rlgl's grid and gizmos in the exact attachments Diligent rendered into — which is what 2.d's depth trap requires. ⚠️ **`rlUnloadFramebuffer` deletes whatever texture it finds on the depth attachment** (verified in `lib/engine/rlgl.h`), and that texture belongs to Diligent; the depth attachment is therefore detached before the FBO is released. Colour attachments are not touched by rlgl, so only depth needs this.
- **The game renders into the same offscreen target and gets blitted, rather than rendering to the backbuffer directly.** `AttachToActiveGLContext` deliberately creates no swap chain ("the application is responsible for presenting the main frame buffer"), so there is no Diligent-side backbuffer to target with a known format. `endScene` blits full-screen when no caller sized a target, which keeps `IRenderer`'s "no explicit target → backbuffer" contract intact. Side effect, deliberate: the target now follows the window size, where `R3D_Init` was handed 800×600 before `MaximizeWindow()` and never resized.

**Matrix convention — decided in 3.a, implemented in 3.b.** Diligent's `float4x4::Projection` is **left-handed**, and its math is row-vector; the engine is right-handed raylib/raymath with column-vector `Matrix`. Rather than converting, the CPU side keeps building view/projection with `MatrixLookAt`/`MatrixPerspective` and uploads the 16 floats, with HLSL written column-vector (`mul(M, v)`) so HLSL's default column-major packing lines up with what rlgl itself uploads. This is **not just convenience: it is required by the overlay**, which depth-tests rlgl geometry against the scene's depth buffer and therefore needs the scene written in rlgl's own `[-1, 1]` NDC depth range. A future Vulkan/D3D backend changes only the CPU-side projection (to `[0, 1]`); the shaders stay as they are.

⚠️ **"The 16 floats" means `MatrixToFloatV(m).v`, not the bytes of the `Matrix` struct — they are transposes of each other.** raylib declares `Matrix` as `float m0, m4, m8, m12; float m1, m5, ...`, so its *storage* order is row-major, while `MatrixToFloatV` reorders to `m0, m1, m2, m3, ...` — the column-major array OpenGL takes with `transpose = false`, and the one `glUniformMatrix4fv` gets everywhere in rlgl. A `memcpy` of the struct would upload the transpose and silently produce a wrong (but plausible-looking) transform. Confirmed on the GLSL side too: the HLSL2GLSL converter only emits `layout(row_major)` when the source asks for it with `#pragma pack_matrix(row_major)`, and its own header notes "by default, all matrices in both HLSL and GLSL are column major".

⚠️ **The GL context is exactly 3.3, and that is raylib's decision, not ours.** The runtime log reads `Attached to OpenGL 3.3 context (3.3.0 NVIDIA 591.86)` followed by `Disabling separable shader programs` — the vendored `libraylib.dll` is built `GRAPHICS_API_OPENGL_33` and GLFW is asked for 3.3 core, so Diligent adopts that context as-is. Consequences for 3.b/3.c: the HLSL→GLSL converter emits `#version 330 core` (the version is derived from the device's actual GL version in `GLSLUtils.cpp`), and SSBOs, compute, and image load/store are unavailable. If DiligentFX's PBR path turns out to need 4.x, the fix is to rebuild the vendored raylib with `GRAPHICS_API_OPENGL_43` — not to work around it in the backend. **HLSL is usable on the GL backend**: DiligentCore links `Diligent-HLSL2GLSLConverterLib` into `Diligent-GraphicsEngineOpenGL-static` (this is a different target from the `HLSL2GLSLConverter` CLI tool that Phase 1 had to `EXCLUDE_FROM_ALL`).

- [x] **3.b Geometry & first PSO.** New backend-neutral `rendering/geometry/`: `meshData.h` (`MeshVertex` + `MeshData`) and `primitiveGenerator.{h,cpp}` (`generatePrimitive`, cube only so far). The Diligent backend gained a `MeshSlot` pool (immutable vertex + index buffer, index count), one `IPipelineState` + `IShaderResourceBinding` for opaque scene geometry, two `USAGE_DYNAMIC` constant buffers (per-frame view-projection, per-draw model), and a `_draws` queue. **Verified**: both backends build clean (exit 0), the editor and the standalone game run with zero Diligent errors or warnings logged, and the cube's silhouette in the editor viewport is pixel-identical between the two builds — same left/right edges, same bottom vertex, same top-face/front-face edge, same triangle seam across the front quad.

**Sub-phase 3.b decisions:**

- **The primitive generators are backend-neutral, under `rendering/geometry/`, not inside the Diligent backend.** They are pure CPU math with no API dependency, and Phase 5 writes the other nine there. Putting them under `backends/diligent/` would mean moving them in Phase 5 and would cost Phase 9 its "delete a directory plus one CMake branch" property. Cost accepted: they compile (unused) into an R3D build until Phase 9.
- **`MeshVertex` is position + normal + uv + `Vector3` tangent, and that is now the contract Phase 5's nine remaining generators write to.** The attribute *set* mirrors DiligentFX's `PBR_Renderer`, whose documented layout is `float3 Tangent : ATTRIB7` — **no handedness `w`**, the bitangent being derived as `cross(normal, tangent)`. Matching that now means the buffers can feed `PBR_Renderer` unchanged and the importer has one convention to hit; the cost is that `tangent` is written but unread until normal mapping lands.
- **Engine shaders are `.hlsl` files copied next to the executable** (`bread_copy_engine_shaders()` in the root `CMakeLists.txt`, `copy_directory` not the assets' copy-if-missing, since they are part of the binary's behaviour), loaded through `IEngineFactory::CreateDefaultShaderSourceStreamFactory` rooted at `GetApplicationDirectory() + "shaders"`. The alternative — DiligentFX's own approach, `convert_shaders_to_headers()` + `MemoryShaderSourceFactory`, which embeds shaders in the binary — was rejected for two reasons: Phase 11's hot-reload wants real files at runtime, and `convert_shaders_to_headers` is defined by DiligentCore's `BuildUtils.cmake`, which is not loaded yet when `add_subdirectory(modules/engine)` runs (DiligentCore is added after it, deliberately, for the zlib reason above). Revisit only if shipping a single self-contained exe becomes a goal.
- **`Diligent-GraphicsTools` is deliberately not linked.** Its `MapHelper` is the idiomatic way to write a dynamic buffer, but it is the only thing that would have been used from a whole static library; `IDeviceContext::MapBuffer`/`UnmapBuffer` through a five-line local helper does the same with no new dependency. Reconsider when something else in that library is actually needed.

**Three real traps found in 3.b, all of them runtime-only — "it builds" caught none of them:**

- ⚠️ **The HLSL→GLSL converter passes C-style casts straight through, and GLSL rejects them.** `mul((float3x3)g_Model, normal)` compiles as HLSL and fails at GL shader compile time with `error C7503: OpenGL does not allow C-style casts`. Diligent reports it clearly (it dumps the full generated GLSL), but only when the shader is created — there is no offline check. Written as `mul(g_Model, float4(normal, 0.0)).xyz` instead, which is also the naive normal transform (correct up to non-uniform scale, which the test scene now deliberately exercises visually). **General rule for every shader from here on: HLSL that is legal for D3D is not automatically legal through the converter** — casts, implicit conversions (`float4 v = 0;`), `float3` struct members and structs passed to functions are all called out in `HLSL2GLSLConverterImpl.hpp`'s "known issues" header comment. Read it before writing anything non-trivial.
- ⚠️ **Diligent's PSO leaves GL state that rlgl believes it still owns, and rlgl only issues the GL calls it thinks are needed.** The scene pipeline disables blending and enables the depth test; rlgl's own state model says the opposite outside a 3D pass. The visible symptom was the *entire editor UI* rendering its text as solid rectangles — the font atlas drawn with blending off — while the 3D overlay looked perfect, because `BeginMode3D` re-enables depth explicitly and blending does not matter for the grid. `yieldToRaylib()` now restores blending and the depth test alongside unbinding. **This generalizes: anything a future PSO sets that rlgl also tracks (cull mode, front face, scissor, depth writes, blend func) has to be restored there too.** Culling and depth writes currently match rlgl's defaults by coincidence, not by design.
- ⚠️ **`InvalidateState()` is needed *before* the Diligent pass, not only after it.** Spike 0.3 established the unbind/invalidate/flush sequence for handing the context back to raylib; the mirror case is just as real, because raylib has been drawing through the same context all the way from the previous `endScene`, so Diligent's cached GL state is stale by the time the scene pass starts.

**Two smaller things worth knowing:**

- The scene projection takes its near/far from `rlGetCullDistanceNear()`/`rlGetCullDistanceFar()` rather than hardcoding `0.01`/`1000`. The editor's overlay depth-tests against this target's depth buffer through raylib's own `BeginMode3D`, which uses those same values — a divergence would show up as grid lines cutting through geometry at the wrong depth.
- Aspect comes from the scene target, not the screen. Note that raylib's `BeginMode3D` derives its aspect from `GetScreenWidth/Height` regardless of the render texture it is drawing into, so the editor's overlay projection does *not* exactly match the scene's when the viewport panel is not the full window. This is pre-existing and identical under both backends, so it does not affect a screenshot diff — but it is the reason the grid and the scene can disagree by a fraction of a degree.

**The checked-in test scene gained a Cube node, and its transform is deliberately non-trivial** (position `{0, 0.5, 0}`, 30° about Y, scale `{1.5, 1, 1}`). A cube at the origin with an identity transform would have made the per-draw constant buffer untestable — the wrong model matrix and no model matrix at all look the same. With the transform, the silhouette comparison against R3D validates the whole `T * R * S` composition and the upload order in one shot. The Capsule and the glTF model still render nothing under Diligent, which is expected: their generators and the model path land in Phase 5. **3.c then gave the Cube the scene's three existing textures** (`scene_albedo.jpeg`, `scene_normal.png`, `scene_omr.png`) — without them nothing in the scene exercised the texture path at all, since the only textured node is the model Diligent cannot draw yet.

- [x] **3.c Forward PBR.** `scene.psh` became a metallic-roughness shader (Trowbridge-Reitz GGX, Smith with Schlick's k, Schlick Fresnel, glTF ORM packing), the backend gained a texture pool backed by DiligentTools' loader, four material texture slots on the pipeline, 1x1 fallback textures and a real light pool. `SceneFrameConstants` now carries the camera position, the light and the ambient term alongside the view-projection; `SceneDrawConstants` carries the model matrix and its inverse transpose. **Verified**: both backends build clean, editor and standalone game run with zero Diligent errors or warnings, and the textured cube's silhouette, UV placement and face-to-face shading match the R3D build. Measured against the R3D capture at the same pixels: editor chrome 245/245/245 and 201/201/201 in both, viewport background 130/130/130 in both.

**Sub-phase 3.c decisions:**

- **The shader is engine-owned, not DiligentFX's `PBR_Renderer` — deliberately, and only for now.** Spike 0.4 decided to drive `PBR_Renderer` directly, and that still stands for Phase 4/5. Adopting it inside 3.c would have meant taking on its PSO flags, its exact `PBRFrameAttribs`/`PBRPrimitiveAttribs` layouts and its SRB conventions in the same step as the first textures — with the GL 3.3 ceiling as an unquantified risk on top (parts of its shader tree reference `gl_DrawID` and structured buffers, which would force rebuilding the vendored raylib as `GRAPHICS_API_OPENGL_43`). ~60 lines of HLSL keeps 3.c's failure modes inside our own code. Phase 4 decides whether they get deleted.
- **Textures load through DiligentTools' `TextureLoader`, split across two threads the way the loader is built for.** `CreateTextureLoaderFromFile` needs no device, so it runs on the shared `WorkerPool` exactly where raylib's `LoadImage` used to; `ITextureLoader::CreateTexture(device, ...)` runs on first use, on the thread that owns the device. That is the same decode-then-upload shape the R3D backend already had, and it brings sRGB handling, mip generation and DDS/KTX for free — the reuse the plan's Phase 4 note predicted.
- **Material textures are `SHADER_RESOURCE_VARIABLE_TYPE_DYNAMIC` variables re-pointed per draw, not an SRB per material.** With no `MaterialHandle` yet (deferred to Phase 4 on purpose) there is nothing stable to key an SRB cache on, and a dynamic variable plus a `CommitShaderResources` between draws is what Diligent provides for exactly this. The variable pointers are resolved once at pipeline creation, since the lookup is by name and the draw loop would otherwise run it per material.
- **No sampler cache.** `IRenderDevice::CreateSampler` already de-duplicates by description (`RenderDeviceBase::CreateSamplerImpl` goes through `m_SamplersRegistry`), so each texture asking for its own is free. Combined texture samplers put the sampler on the *view*, which is what makes a per-texture filter/wrap reach the GPU at all.
- **The fallback textures reproduce `R3D_MATERIAL_BASE` exactly** — white albedo, flat normal, occlusion 1 / roughness 1 / metalness 0, no emission — so an untextured material shades the same under both backends rather than differing by a default nobody chose.

⚠️ **The 3.b comment about tangent handedness was wrong, and it is fixed.** It claimed the bitangent is `cross(normal, tangent)`. DiligentFX derives it the other way round — `float3 b = normalize(cross(t, n))` in `ShaderUtilities.fxh`, and `cross(Tangent, Normal)` in `RenderPBR.psh` — which is also what the cube generator actually produces and the direction v increases in. Left as written, every normal map's green channel would have been inverted.

**Three more pieces of GL state Diligent changes globally and rlgl knows nothing about.** All three are the same class as 3.b's blend/depth finding, all three were invisible until something drew, and all three needed raw GL to undo — so the backend now links `GLEW::glew`, the loader DiligentCore already initializes against the shared context (its `GLEW_STATIC` define and include directory are `PUBLIC`, and the function pointers are global, so linking the same static target is enough — no second `glewInit`).

- ⚠️ **Diligent binds a sampler object per texture unit, and a leftover one blacked out the entire editor UI.** rlgl uses no sampler objects at all and relies on each texture's own parameters; a bound sampler overrides them, and its mipmapped minification filter makes raylib's single-mip textures *incomplete*, which samples as opaque black. The symptom was total: every panel, every glyph, the whole chrome, while the 3D viewport still rendered. `yieldToRaylib()` now unbinds the sampler on every unit the material slots use. **Note that `InvalidateState()` does not help here** — it resets Diligent's *cache* of the GL state, not the GL state itself, which is the whole reason these restores have to be explicit.
- ⚠️ **Diligent leaves `GL_UNPACK_ROW_LENGTH` set to the stride of whatever it uploaded last, and that silently blanked every glyph in the editor.** `Texture2D_GL.cpp` sets it per upload (`SubresData.Stride / PixelSize`) and never restores it; raylib sets only `GL_UNPACK_ALIGNMENT` before its own uploads, because it has always been able to assume the default row length of 0. The 1x1 material fallbacks leave it at **1**, so raylib's next `glTexImage2D` walks its source one pixel per row — which reduces the font atlas to nothing. The symptom is unusually specific and worth recognizing: **panels, borders and icons all render correctly while text is completely absent**, because raygui draws its icons as rectangles through rlgl's default 1x1 texture (created at `InitWindow`, before Diligent existed) and the font atlas is the only thing the editor uploads itself. `restoreRaylibPixelStore()` now runs after every point Diligent is handed pixels — the fallbacks at startup and each texture upload in `finalizeTexture`. Note this one is *not* fixable in `yieldToRaylib()`: fonts are loaded during editor init, before any frame is yielded.
- ⚠️ **Diligent enables `GL_FRAMEBUFFER_SRGB` once at device creation and deliberately never turns it off** (`RenderDeviceGLImpl.cpp`: "this setting should be just set once and left that way"). That is sound for its own targets — the conversion is a no-op for non-sRGB formats — but raylib's colours are already encoded, so everything rlgl drew to the window was being gamma-encoded a second time. **This is the real explanation for the 3.a note that "the Diligent gray reads slightly lighter than r3d's for the same 130,130,130"** — it was not tonemapping. Measured: the viewport background read 189 with it on, and exactly 130 (r3d's own value) with it off.

**One real bug in the BRDF, worth knowing because the wrong form is the common one.** Writing the specular term as `D*G*F / max(4*nDotV*nDotL, eps)` and then multiplying the whole result by `nDotL` breaks the cancellation those two `nDotL`s are supposed to do: wherever the light only grazes a surface the clamp takes over and leaves a bright rim. Measured on the test cube's side face: 61/55/63 with the clamp, 0/0/2 without it. The term is now `D*G*F / (4*nDotV)` with `nDotL` applied to the diffuse lobe only, which is the same equation with nothing to clamp.

**Colour response is the one thing that does not match r3d, and it is now a project setting rather than a hardcoded choice.** The shader encodes its linear result before writing to the plain UNORM scene target. r3d's tonemap in the checked-in scene is mode `Linear` with exposure 1, so r3d writes linear values straight out and its lit surfaces read near-black (0-1 where a gamma-encoded pass reads 28-47 for the same dark albedo). Geometry, UVs, face-to-face shading, chrome and background all match exactly; only the surface response differs, because r3d is not gamma-correcting.

`ProjectSettings::outputColorSpace` (`OutputColorSpace::Gamma | Linear`, **defaulting to Gamma**) now decides it, and `IRenderer::setOutputColorSpace` carries it across the seam. Details worth knowing:

- **It is pushed from `Engine::initialize`, right after the validator, and not before.** `Renderer::initialize` runs several lines *earlier* than the project settings are loaded, so the renderer cannot read the value at construction. Consequence: editing the field in the inspector takes effect on the next launch, which the field's own comment says.
- **It reaches the shader as a constant, not a shader permutation** — one exponent in the frame block (`1/2.2` or `1.0`), so there is no PSO to rebuild when it changes. `pow(color, 1.0)` is a wasted instruction in Linear mode and that is the whole cost.
- **Adding the field does not break existing `.cnf` files.** `InspectorStruct::deserialize` guards every property with `if (node[prop.name])` ([inspectorObject.cpp:88](modules/engine/inspectorObject.cpp)), so a config written before the field existed simply keeps the C++ initializer — Gamma. Worth remembering as the general rule for adding settings: **new inspector fields are backward compatible; only removing or reordering enum values is not.**
- The R3D backend implements the call as a no-op, because what r3d writes is decided by the environment's own tonemap block, which already goes through `setEnvironment`.
- Known inconsistency in Linear mode, inherited rather than introduced: the background is cleared with the raw (already-encoded) colour while shading writes linear. That is exactly r3d's own behaviour, which is what the mode exists to reproduce. Gamma mode is the self-consistent one, and proper tonemapping belongs in front of the encode in Phase 7.

**The test scene is now a checked-in asset — the gap 2.a flagged is closed.** `games/example_game/assets/` carries `Root.nd`, `assets_registry.cnf`, `project_settings.cnf` and `global_light_settings.cnf`, so `CopyMissingAssets.cmake` seeds every build directory with the same scene and the same asset GUIDs. The scene is a Capsule primitive at `x = -3`, a transformed Cube primitive at the origin (added in 3.b, see below), the `scene.gltf` model (albedo + normal + ORM, 4096²) at `x = +3`, and a directional SunLight — one node per rendering path the migration has to keep working. `editor_settings.cnf` is deliberately *not* checked in (it is editor-local and was empty); the registry heals itself by re-adding it with a fresh GUID on first run, which is safe because nothing references it. **To update the scene, edit it in the editor and copy those four files back out of `bin/assets/game/`** — `copy_missing` only copies what is absent, so it will never overwrite build-directory state.

Getting there needed a real fix first, and it applies to any checked-in project, not just this scene:

- ⚠️ **The assets registry baked absolute paths, so it could only ever load on the machine and in the directory that wrote it.** `deserializeConfig` computed `_projectPath` correctly from the config file's own location and then immediately overwrote it with the serialized one, and every `File`/`Folder` carried a serialized absolute `_fullPath`. Checking that in would have produced a registry that resolves to `cmake-build-debug` on every machine — and when the paths do not exist, `removeUndefinedFoldersAndFiles` strips the whole tree, which loses exactly the GUIDs the scene's asset links resolve through. **Fixed by making the registry relocatable**: `_projectPath` and `_fullPath` are no longer serialized at all (they are fully derivable), the runtime `_projectPath` is kept, and `AssetsConfig::restoreFullPaths` rebuilds every absolute path from `_projectPath` + the still-serialized `_pathFromRoot` before the indexes are built. Old registries with the extra keys still load — the keys are simply not read — and are rewritten in the new form on first save, so no migration is needed. Verified by wiping `bin/assets/game/` in the Diligent build directory, re-seeding from source, and confirming the model and its three textures resolve to the same GUIDs under a completely different absolute path.
- One consequence worth knowing: a **binary built before this change crashes on a registry written after it** (`invalid node; first invalid key: "_projectPath"` — yaml-cpp throws on the missing key). New code reads old files fine; the reverse is not supported.
- `games/example_game/main.cpp`'s hardcoded camera moved from `{10, 1, 1}` to `{0, 2, 12}` looking at `{0, 0.5, 0}`, so the game frames the two objects side by side the way the editor viewport does instead of stacking them along its own view axis.

### Review pass between 3.a and 3.b

A code-quality review and a bug hunt were run over `rendering/`, `systems/`, `engine.cpp`, `editor.cpp` and the example game before starting 3.b. Everything below is fixed and verified (both backends build, editor and game screenshot-match their pre-fix captures on the checked-in scene, zero errors logged).

- ⚠️ **The relocatable-registry change from 3.a turned a latent bug into data loss, and that is now fixed.** `renameFile` / `renameFolder` / `moveFile` built a child's `_pathFromRoot` as `parent->_pathFromRoot + "\" + name`, but the root folder's `_pathFromRoot` is the display string `"Project Files"`, not a path — so anything renamed at the project root became `"Project Files\X"`. `renameFolder` also guarded on `folder->getDepth() == 0` when a top-level folder has depth **1**, so its guard never fired, and it never assigned `_fullPath` at all (making `renameInternal` a `rename(X, X)` no-op). While `_fullPath` was serialized this was cosmetic; once `_pathFromRoot` became the only source of truth, a single rename made the registry unloadable, which strips the tree and re-registers every file with **fresh GUIDs** — silently breaking every asset link in the scene. Fixed with one `childPathFromRoot(parent, name)` and one `toFullPath(pathFromRoot)` used at every site that assigns either field, so `_fullPath` is always derived and the two can no longer diverge.
- **`Logger` stored a `std::string_view` into raylib's rotating `TextFormat` buffer** (4 buffers), so every retained entry was garbage after four more log lines. Note this **invalidates what the 2.a notes claimed**: the function-local `static std::string` in `renderer.cpp` was not a workaround, because `Log()` re-wrapped the message through `TextFormat` regardless. `LogEntity::message` is now a `std::string`, which fixes every call site at once; the two statics are gone.
- **`Renderer::get()` no longer initializes on demand.** It was a second, invisible init path with different arguments, and for Diligent it would attach to a GL context that may not exist yet (failing several frames later) or resurrect the backend after `shutdown()`. It now throws, matching the `Logger::LogError` + `throw std::runtime_error` idiom already in `assetsConfig.cpp`. Both entry points call `Engine::initialize` first, so nothing legitimate reaches it.
- **`CreatePrimitiveCommand` ran its parameter panel on a detached thread** that dereferenced `this` (use-after-free after undo), queued a closure capturing the worker's stack `MeshPrimitiveData` **by reference** onto the main thread, called `IsKeyPressed` off the main thread, and raced on `isChangedFromEditor`. Rewritten synchronously: `Command` gained a `virtual void update()` ticked by `CommandsHandler::update()`, and the command owns its data in a `unique_ptr`. The ten near-identical switch arms collapsed into one `createData` factory, with the node name coming from `magic_enum::enum_name` (so "FreePoly Mesh" is now "FreePoly").
- **One decode thread was spawned per texture.** New `utils/workerPool.{h,cpp}`: a bounded pool (≤4 workers) shared by both backends, joined from `Engine::shutdown`. `TextureSlot` holds a `std::future<void>` instead of a `std::jthread` — ⚠️ **a dropped future does not wait, where the `jthread` destructor did**, so every path that frees or recycles a slot must wait on the job first; all of them already do, and the member carries a comment saying so.
- **`MeshRenderer`'s loaded state had four overlapping sources.** `_isLoaded` is gone — `isLoaded()` is now `_mesh.isValid() || _model.isValid()`, the handles being the authority that 2.b's zeroed-handle fix established. A new `_loadAttempted` latch stops a *failed* model load from re-importing the file every frame. `setGeneratedMesh` now clears `_meshAsset`, enforcing the "either a primitive or a model, never both" invariant the header already claimed, and the primitive path seeds one material when a scene file carries none (the draw path indexes slot 0 unconditionally). `MeshRendererSystem` unloads-then-loads once per frame, leaving `ResetChangedFromEditorSystem` the only clearer of `isChangedFromEditor`.
- **`getModelMaterialCount` takes a `ModelHandle` instead of a path.** It was the only seam method taking a filesystem path while owning no GPU resource, and in a Diligent backend it would have dragged assimp into the GPU backend purely to answer a question about a file — against the Phase 5/9 goal of scoping assimp to import time. `MeshAsset` now loads and destroys the model around the query; same work r3d did internally, only visible, and it runs once per newly registered model.
- Smaller: `EnvironmentSettings` passes by `const&` on `IRenderer` and both backends (const binds the bundle, not the blocks it refers to, so `applyDefaultEnvironment` still writes through); `cameraSystem.cpp` maps `ProjectionType` through a new `toRaylibProjection` instead of `static_cast<int>`, which only worked because the declaration order — a *serialization* contract — happened to match raylib's enum; `onFrameStart`/`onFrameEnd` test the two game render callbacks independently, where a module exporting only one used to get neither.
- **The Diligent backend binds and clears in `endScene`, not `beginScene`.** The engine pushes the environment (and with it the background colour) from a start-frame system that runs *after* `beginScene` returns, so the clear used the previous frame's colour. This is also where the collected draws will be submitted from 3.b on.

Still open, deliberately: `Material::unload()` tears down `TextureAsset`s other materials may share, so any inspector edit on a model re-imports it and re-decodes its textures — the right fix is refcounting in `TextureAsset`, not in the seam. Also unaddressed: a light on a *deactivated* node stays lit (`LightState::active` is unreachable because both the registry and `LightSystem` skip inactive nodes), and `CameraDirectorSystem` accumulates camera pointers across frames — both belong with Phase 6's light/camera work.

**Background colour will not match exactly until Phase 7.** 3.a clears to `EnvironmentSettings::background.color` raw, where r3d runs its background through tonemapping and colour grading — so the Diligent gray reads slightly lighter than r3d's for the same `130,130,130`. Compare geometry, framing and shading for now; colour-exact diffs are a Phase 7 expectation.

### Phase 2 — agreed shape (decided before any code was written; don't re-litigate silently)

- **Backend switch is compile-time, not runtime.** `BREAD_RENDER_BACKEND` CMake cache option (`R3D` | `Diligent`, defaults to `R3D`), which sets `BREAD_RENDER_BACKEND_R3D=1` / `BREAD_RENDER_BACKEND_DILIGENT=1` as a `PUBLIC` compile definition on `BreadEngine` (so editor and game inherit it). Exactly one backend's `.cpp` files are compiled — `modules/engine/CMakeLists.txt` filters `rendering/backends/` out of the `GLOB_RECURSE` and adds back only the selected directory. Rationale: r3d gets deleted outright, so the inactive backend must not survive as dead code in the shipped game. **Consequence for QA: screenshot-diffing R3D vs Diligent means two build directories, not an env var** — which applied through Phase 3 and stops there, see the ⚠️ note under the Phase 3 sub-phase split. The switch itself outlives its purpose in Phase 3.6, where deleting r3d leaves it single-valued.
- **Sub-phase order** (each one builds, runs and is verified before the next starts): **2.a lights** ✅ · **2.b resources & draw** ✅ · **2.c environment/skybox** ✅ · **2.d frame lifecycle & call sites** ✅.
  Textures/materials and meshes/draw were originally planned as two separate sub-phases. They were merged into 2.b because they cannot be split: a material only reaches the GPU through a draw call, so doing materials first would have meant writing a temporary `MaterialData → R3D_Material` adapter for `meshRendererSystem` and deleting it one sub-phase later.
- **`Material` stays a value struct**, holding engine-native material data plus `TextureHandle`s; the renderer translates it at draw time. A real `MaterialHandle` is deferred to Phase 4, where it becomes an SRB and actually means something — introducing a pool wrapper around a plain struct now would be ceremony. Its `_uvOffset`/`_uvScale`/`_alphaCutoff` fields were **removed** after 2.b: they were placeholders that were serialized but never reached the renderer, and dropping them also cleared the `_uvScale: {0, 0}` values out of saved assets, so they can be re-added later with correct defaults and no migration.
- **`configs/light`'s R3D enums were originally deferred to Phase 7 — that was reversed in 2.c**, which had to convert them (see the 2.c entry for why). Nothing outstanding here.

### Phase 2 decisions taken in 2.d (both are shape-of-`IRenderer` calls — don't undo them silently)

- **The renderer owns the offscreen scene target; the caller never hands it one.** `resizeSceneTarget(w, h)` establishes it, and `beginScene` renders into it when it exists and to the backbuffer when it doesn't — which is exactly `R3D_BeginEx`'s own documented "invalid target → screen" behaviour, so one entry point serves both the editor and the game. The alternative (caller supplies a `RenderTexture2D`) was rejected because a raylib FBO is something a Vulkan/D3D Diligent backend physically cannot render into. This matches spike 0.3: Diligent owns an `ITexture` and hands out something wrappable as a raylib `Texture2D`.
- **`beginSceneOverlay()`/`endSceneOverlay()` exist, and they are GL-family-only by nature.** They make the rendered scene the active raylib draw target so the editor's grid and gizmos draw on top of it *with the scene's depth buffer still bound*. See the depth finding below for why this is not optional. They are editor-only (the game never calls them) and the editor is an OpenGL-backend process by the Phase 0.3 decision, so this is implementable for Diligent too — but a Vulkan/D3D backend must be free to no-op them, and `viewportWindow`'s gizmo/grid pass would then need Phase 8's "overlay after the blit" treatment instead.

**2.d verification, and the depth trap it exposed.** Screenshot-compared against the 2.c capture on the same Capsule + directional-light scene, and the game run separately.
- ⚠️ **Handing the scene to the editor as a colour texture silently drops the depth buffer.** The first attempt (renderer blits its scene texture into an editor-owned raylib canvas, editor then draws grid/gizmos into that canvas) built and ran fine, but the screenshot showed grid lines drawn straight *through* the capsule — the overlay had nothing to depth-test against, because only colour had been copied. Before the seam this worked by accident of colocation: r3d wrote colour **and depth** into the very render texture the editor then drew into. Fixed with the overlay brackets above. **This is a permanent property of the architecture, not an r3d quirk** — any design that moves the scene between the renderer and an rlgl overlay as a texture has it, so Phase 8 must either keep the overlay brackets or move the grid into the renderer as real scene geometry (the cleaner long-term answer, since a grid is scene content and gizmos legitimately want to draw on top).
- A second, smaller trap from the same attempt: the target is an FBO texture, so it needs exactly one vertical flip on its way to the screen. Two chained blits (scene → canvas → panel) each flipping cancelled out and rendered the viewport upside down. With the overlay design there is only one blit and one flip, which is what `drawSceneTexture` does.

**Serialization risk from the original plan — RESOLVED, and the reason generalizes.** The plan flagged `INSPECT_FIELD(lightType)` on a raw `R3D_LightType` as a real migration risk for existing scene files. Zeroing the handle (which a handle-based design does by construction) turned the latent UB into a visible disappearing capsule. Fixed by renaming `loadModel()` → `load()` and having it rebuild from `_meshPrimitiveData` when there is no mesh asset.

**Real build-system gotchas hit and fixed (not hypothetical, all order/global-scope issues — worth remembering since they can resurface if CMakeLists.txt structure moves around later)**:
- **Global `include_directories()` was actively dangerous once a third-party tree with generically-named headers entered the build.** Root `CMakeLists.txt` had a blanket (non-target-scoped) `include_directories()` listing `lib/engine/assimp` among others. Assimp ships its own generic `texture.h`; because that path came before DiligentCore's own include dirs on every subsequently-added target's command line (`include_directories()` leaks into every `add_subdirectory()` after it, including vendored third-party ones that never asked for it), DiligentCore's `#include "Texture.h"` resolved to **assimp's** `texture.h` instead of its own (Windows include paths are case-insensitive), breaking `EngineFactoryBase.cpp` with a bogus "undeclared identifier `TextureDesc`" error. Fixed by deleting the blanket block entirely — every path in it was already redundant with an existing `target_include_directories()` in `modules/engine/CMakeLists.txt` (PUBLIC, so it propagates to `BreadEditor`/`ExampleGame` via linking `BreadEngine`) or `modules/editor/CMakeLists.txt`. **Lesson: never use bare `include_directories()` in this project going forward** — always `target_include_directories()`, scoped to the target that actually needs it.
- **This project's own code had a latent, identically-shaped bug**: `modules/engine/models/reservedFileNames.h` and `modules/editor/models/reservedFileNames.h` are two different classes with the same filename. `modules/engine/configs/assets/file.h` included it as a bare `"models/reservedFileNames.h"`, which is fine when compiled as part of `BreadEngine` (whose own include order never sees the editor's copy) but broke once compiled as part of `BreadEditor`'s translation units (which put `modules/editor` before `modules/engine` on the command line) transitively via `assetsConfig.h` — resolved to the wrong (editor's) class. This was silently relying on the old blanket `include_directories()`'s ordering to paper over it. Fixed by making `file.h`'s include explicit/relative (`"../../models/reservedFileNames.h"`), matching the explicit-relative-path style already used elsewhere in this codebase for exactly this reason (e.g. `renameAssetCommand.h`'s `"../../../engine/configs/assets/assetsConfig.h"`). No other ambiguous same-name-header usage found (`cameraSystem.h` also exists in both trees, but every usage resolves via the "check the including file's own directory first" quote-include rule, so it was never actually ambiguous).
- **DiligentTools vendors its own zlib** (`ThirdParty/zlib`, for `TextureLoader`'s PNG support) which collided with `cpptrace`'s bundled `libdwarf` (FetchContent'd in `modules/engine/CMakeLists.txt`): `libdwarf`'s own bare `find_package(ZLIB)` (no `REQUIRED`) would pick up DiligentTools' local, non-exported zlib target instead of finding nothing (as it always had before Diligent existed in this tree). This showed up two different ways depending on CMake version: with system CMake 3.30, `libdwarf`'s `export(EXPORT libdwarfTargets ...)` failed at generate time (the picked-up target isn't part of any export set); with **CLion's bundled CMake 4.2** specifically, generate succeeded but the final executable link failed with `clang++: error: no such file or directory: 'ZLib'` (`ZLIB_LIBRARY` resolved to a bare, pathless token instead of a real path/target reference). Reordering `add_subdirectory()` calls alone was **not** a reliable fix across CMake versions — the actual fix is `set(CMAKE_DISABLE_FIND_PACKAGE_ZLIB ON)` immediately around `add_subdirectory(modules/engine)` (turned back `OFF` right after), which deterministically makes `libdwarf`'s `find_package(ZLIB)` report "not found" regardless of CMake version, restoring its pre-Diligent behavior. DiligentTools' own `libpng`→zlib linkage (which needs `find_package(ZLIB)` to succeed against its local vendored target) is unaffected since the disable is re-toggled off before DiligentTools is added. **Lesson: if this resurfaces, don't trust "it built once" as proof — verify with the exact CMake binary/version actually used to build (CLion bundles its own, separate from any system-wide `cmake`), since `find_package()`/target-resolution edge cases like this one are version-sensitive.**
- **DiligentCore always builds a `-shared` DLL variant alongside every `-static` target**, even though nothing needs them here. On this MinGW-w64/clang64 toolchain (`MINGW_BUILD` correctly auto-detected), the shared-lib link step passes `LINKER:--version-script=export.map` — a GNU-`ld`-only flag that this toolchain's linker (`lld`) rejects, breaking `GraphicsEngineVk`/`GraphicsEngineOpenGL`/`Archiver`/`SuperResolution`'s shared variants. Fixed by `set_target_properties(... EXCLUDE_FROM_ALL TRUE)` on those four targets right after `add_subdirectory(DiligentCore)`, since only the `-static` targets are ever linked against.
- **DiligentTools' standalone `HLSL2GLSLConverter` CLI tool doesn't build under MinGW/clang64** at all — it calls MSVC-only CRT debug-heap APIs (`_CrtSetDbgFlag`) that MinGW-w64's CRT doesn't provide. Not needed (Diligent's DXC-based cross-compilation is the actual shader path for later phases), so also `EXCLUDE_FROM_ALL`'d.
