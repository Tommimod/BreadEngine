# Migration plan: r3d → DiligentEngine

**This is the working document**: where the migration stands, the rules that must not be broken, and what is still planned. Keep it short enough to read in full at the start of every session.

The record of how each completed phase went — what broke, how it was found, what was verified — lives in [DILIGENT_MIGRATION_LOG.md](DILIGENT_MIGRATION_LOG.md). That file is history: open the section for an area before working in it, never end to end.

## Status

**Phase 6 — COMPLETE. Every light type casts, all four sub-phases verified on screen.**

The single hard-coded directional light is gone. All three types shade, from a fixed-size array in a constant buffer, with `intensity`, `range`, `spotAngle` and `spotBlend` all live; the shader loops them and accumulates. Directional shadows are DiligentFX's `ShadowMapManager` with four cascades and varying PCF driven by the light's `shadowSoftness`, and `MeshRenderer::castShadows` decides what goes into the depth pass. Spot shadows are one slice of a four-slice array per shadow-casting spot, projected through the cone's own field of view. Omni shadows are a cube of a four-cube array per shadow-casting point light, six 90° depth passes each — and **no matrix reaches the shader for them**: the depth a cube face writes depends only on the largest component of the direction to the surface, so the scene pass rebuilds it from two coefficients and never learns which face it landed on.

Seven decisions were the project owner's, all taken as recommended: directional CSM **plus spot** shadows in 6.c, a fixed-size cbuffer array over per-draw culling, `castShadows` on `MeshRenderer` but no `receiveShadows`, varying PCF driven by `shadowSoftness` over a fixed 3×3 kernel, and for 6.d projected depth over a distance-in-a-colour-cube, four omni casters at 512² faces, and a five-tap disk. `IRenderer::drawMesh` became `drawMesh(const MeshDrawDesc &)` to carry the flag — also the owner's call, over a sixth positional parameter.

**Four defects were found by the owner in the editor afterwards and fixed.** A constant-buffer overflow that crashed the process at random (the shadow block was sized before 6.c grew it); two in the spot path — the near plane was derived from the light's `range`, which put it past every caster once a light was given a long reach, and the PCF kernel had no upper bound; and in 6.d a depth bias applied in the wrong direction, which made every caster shadow itself completely. All four are in the log; the rules behind them are in Invariants.

**Before 6.d — raylib 6.0, and the context moved to OpenGL 4.3.** The vendored raylib went from 5.5 to 6.0, rebuilt as `GRAPHICS_API_OPENGL_43`, so the context GLFW creates and Diligent attaches to is 4.3 core and the engine's shaders now compile as `#version 430 core`. **6.d forced it**: cube map arrays are not core in 3.3, and the one escape hatch does not exist on the GL path — `GLSLUtils.cpp` emits `#extension` directives only on ES, so `samplerCubeArrayShadow` was unreachable no matter what the driver exposed. It also settles the question Phase 7 had open, a phase early: `bitfieldReverse`, compute shaders and SSBOs are all available now, which is what the IBL precompute and DiligentFX's PostFX components need.

`lib/engine/` keeps exactly the shape it had — four headers and one `libraylib.dll`, no submodule — and the build recipe is under "How to work on this". **Nothing in `modules/` changed but one stale comment.** `rlgl.h`'s public header is identical under `_33` and `_43`, so no consumer needed a new define, and the renderer already read its clip range from `rlGetCullDistanceNear/Far` rather than repeating the numbers, which is why raylib moving those defaults from 0.01/1000 to 0.05/4000 cost nothing. **Verified by the project owner in the editor: no visual change of any kind.** Which is the result to want here — a version bump this size earns its keep by what it unblocks, not by what it alters.

**Phase 5 — COMPLETE.** All six remaining generators and the assimp importer. The model path moved *in front of* the seam: `ModelHandle` and its four methods are gone, `createPrimitive` went with them, and `IRenderer` has one `createMesh(const MeshData &)` instead. `MeshAsset` owns a model's buffers with `acquire`/`release` refcounting, `MeshRenderer` holds a list of `MeshPart`, and assimp is now reachable only from import-time code — which is the precondition Phase 9 needs to drop it from the shipped runtime.

Three defects were found in the editor afterwards and fixed: toolbar-created primitives had no `MeshRenderer` at all, `Node::add<T>()` handed back components with a null `_owner`, and imported UVs were flipped. An imported model's materials now take the textures the model file declares. All four are in the log; the rules behind them are in Invariants.

**Between phases — materials became project assets.** A deliberate detour off the plan, taken at the project owner's request before Phase 6. A material is now a `.mat` file: `MaterialAsset` holds the fields the inspector used to show on each renderer, and `MeshRenderer`/`SpriteRenderer` hold a `MaterialLink` naming one, so one edit reaches every slot that links it. Created from the assets window's folder menu ("Create Material"). Three consequences worth knowing before working nearby: the assets system now distinguishes registry-stored from self-stored assets (see Invariants), `MeshAsset` no longer carries materials at all — Phase 5's `wireTextures` auto-wiring is deleted and an imported model draws with the default material until a `.mat` is linked — and `MaterialLink::_isInstanced` is a placeholder that does nothing yet. The log has the four decisions and what was verified.

**After 6.c — a bug-hunt pass over the render path, at the project owner's request.** It started from one symptom the owner remembered (a light kept shining after its node was deactivated) and found that symptom was one of three faces of the same root: **a light is the only render resource whose state the renderer keeps between frames.** Everything else is re-submitted per frame, so skipping it stops it drawing; skipping a light leaves the last value in place. Fixed: `LightSystem` moved from the update phase to start-frame, `Light` gained the `onDestroy` it never had, `CameraDirector` stopped handing out a camera on a deactivated node, and all three handle-owning components gained explicit copy/move operations. The log has the full pass, including the two fixes that were wrong on the first attempt and what caught them.

**Next:** **Phase 7 — environment, skybox, post-processing.** Nothing in Phase 6 is left open.

**What renders today under Diligent:** all seven primitives and imported models, textured, with normal mapping, lit by up to 32 directional/spot/omni lights with range and cone falloff, with cascaded shadows from one directional light, shadow maps for up to four spots and cube maps for up to four omni lights — in the editor viewport and in the standalone game. Still stubbed: skybox and cubemaps, ambient/IBL, and all post-processing.

**Screenshot-diffing against R3D is over**, and as of 3.6 there is no R3D left to diff against at all. It ended with 3.c: nothing past textures and basic lighting was ever built on r3d on a real scene. From here, verify against known-good reference output and the scene's own expected behaviour.

## Open decisions (owner: project owner, not the agent)

Nothing here is open any more — see Status and the recipe under "How to work on this".
- **~~Point/spot shadow priority~~ — fully settled and built.** Spot shadows landed in 6.c, omni shadows in 6.d, the latter as a real cube shadow map rather than the cheaper six-spot-slices variant. Chosen by the project owner on genre grounds: a candle, a bare bulb and a table lamp are all point lights, and for a horror game that is the light that has to cast. Nothing here is open any more.
- **Where the shadow-quality knobs live.** `SHADOW_DISTANCE`, the cascade count, all three shadow-map resolutions and the two per-kind caster budgets are constants in `diligentRenderer.cpp` today. `GlobalLightSettings` is where they would belong if they should be per-project. **Now large enough to be worth pricing:** four omni casters are 24 full-scene depth passes per frame on their own, and nothing culls a caster against a light's range yet.
- **Who owns the shipped game's 2D** — the gap under Phase 9. Must be answered before the game loses rlgl.
- **A separate MSVC toolchain for D3D** — spike 0.1 found ATL is missing in clang64, so D3D11/D3D12 cannot build here at all. Vulkan+GL covers PC and SteamDeck.

## Invariants

Rules already paid for in bugs. Breaking one of these does not produce a compile error — it produces a silent, visual, or data-loss failure weeks later. The log has the incident behind each.

**Serialization**

- **Enums serialize by *declaration index*** (`magic_enum::enum_index`), not by name and not by underlying value. **Append only, and delete only from the tail** — removing a middle value silently reindexes everything after it. An out-of-range index deserializes to the field's default rather than crashing.
- **New inspector fields are backward compatible.** `InspectorStruct::deserialize` guards every property with `if (node[prop.name])`, so a config written before a field existed keeps the C++ initializer. Removing or reordering is what breaks.
- **The assets registry must stay relocatable.** `_projectPath` and `_fullPath` are derived and never serialized; `_pathFromRoot` is the only source of truth. Every site that assigns either must go through `childPathFromRoot` / `toFullPath` — a divergence makes the registry unloadable, which strips the tree and re-registers every file with fresh GUIDs, breaking every asset link in every scene.

**Matrices and geometry**

- **Upload `MatrixToFloatV(m).v`, never the bytes of the `Matrix` struct** — they are transposes of each other. Shaders are written column-vector, `mul(M, v)`, which lines up with HLSL's default cbuffer packing and with what rlgl itself uploads. The struct declares its fields row by row (`m0, m4, m8, m12` first) while `MatrixToFloatV` emits them in index order, so `memcpy` between a `Matrix` and any float array is silently a transpose. Anything crossing into or out of Diligent goes through `float16`.
- **What Diligent stores for `v * M` and what the engine uploads for `mul(M, v)` are the same sixteen floats.** Diligent is row-vector with row-major storage; raylib is column-vector with `MatrixToFloatV`'s ordering; the two conventions differ by exactly one transpose each, and they cancel. So a Diligent `float4x4` copies straight into a `float16` and stays usable as `mul(M, v)` — **provided the producer was asked not to transpose it**. `ShadowMapManager::DistributeCascadeInfo::PackMatrixRowMajor` defaults to *false*, which transposes on the way out; the renderer sets it **true**. Get that wrong and every shadow lands somewhere plausible but wrong.
- **DiligentFX's camera space runs +Z forward; the engine's runs −Z.** `GetFrustumMinimumBoundingSphere` returns a centre at `(0, 0, +FarPlane)` and `GetNearFarClipPlanes` reads a left-handed projection, so handing `DistributeCascades` the engine's own view matrix puts every cascade behind the camera. `renderCascades` builds a left-handed basis and a `float4x4::Projection` for it instead, and the pixel shader gets its camera-space depth from `dot(worldPos - cameraPos, cameraForward)` rather than from a view matrix — which is handedness-free and needs nothing uploaded but the forward axis.
- **The scene projection stays OpenGL's `[-1, 1]` depth range** for as long as the editor's rlgl overlay depth-tests against the scene's depth buffer. Near and far come from `rlGetCullDistanceNear/Far` so the two projections agree — **asked for, never written down**. That was tested by raylib 6.0 moving those defaults from 0.01/1000 to 0.05/4000: no code changed, because `beginScene` and `renderCascades` both ask.
- **Vertex layout is the contract for every generator and the importer**: position, normal, uv, and a `float3` tangent with no handedness. The bitangent is `cross(tangent, normal)` — the direction v increases in, and what DiligentFX's own shaders build their TBN with. Front faces are counter-clockwise.

**Sharing an OpenGL context with raylib**

- **rlgl tracks GL state in software and only issues the calls it believes are needed.** Anything Diligent changes that rlgl also tracks must be put back in `yieldToRaylib()` — currently blending, the depth test, bound sampler objects and `GL_FRAMEBUFFER_SRGB`. Culling and depth writes happen to match rlgl's defaults today; that is coincidence, not design.
- **`InvalidateState()` resets Diligent's *cache* of GL state, not the GL state itself.** It is needed before the pass as well as after, and it is never a substitute for an explicit restore.
- **Pixel-unpack state must be restored at every upload site, not in `yieldToRaylib()`.** Diligent leaves `GL_UNPACK_ROW_LENGTH` set to its last stride; raylib assumes the default. Fonts load during editor init, before any frame is yielded — the symptom is the whole UI rendering correctly *except* that text is completely absent.
- **The GL context's version is raylib's decision, and only raylib's.** It is 4.3 core today because `lib/engine/libraylib.dll` is built with `GRAPHICS_API_OPENGL_43` and GLFW asks for exactly that (`rcore_desktop_glfw.c`, the `RL_OPENGL_43` branch), so compute, SSBOs, image load/store and cube map arrays are all in reach. **`rlgl.h`'s public header is identical under `_33` and `_43`** — every difference is inside `RLGL_IMPLEMENTATION` — so no consumer defines it and none should. Anything needing more than the context gives is a raylib rebuild, never a workaround in the backend.

**Shaders**

- **HLSL that is legal for D3D is not automatically legal through the GL converter.** No C-style casts, no implicit conversions (`float4 v = 0;`), avoid `float3` members in cbuffer structs, do not pass structs to functions. `HLSL2GLSLConverterImpl.hpp`'s known-issues header comment is the list — read it before writing anything non-trivial.
- Sources live as `.hlsl` files next to the executable and are compiled at runtime, so a shader edit does not need a rebuild.
- **`GL_SUPPORTED` must be defined by hand for any DiligentFX shader header.** Nothing in the GL path defines it, and an undefined macro is zero to the preprocessor — so `PCF.fxh` silently takes its D3D branch and emits `Texture2DArray.SampleCmpLevelZero`, which the converter's own known-issues list names as having no GLSL counterpart at all. The renderer passes it from `IsGLDevice()`.
- **Including a DiligentFX `.fxh` needs the compound source factory**, because those files are compiled into the static library rather than shipped next to the executable: `CreateCompoundShaderSourceFactory({&DiligentFXShaderSourceStreamFactory::GetInstance(), <the file factory>})`. The engine's own `shaders/` directory is the second factory in that list.
- **Screen-space derivatives are only defined where control flow is the same across a quad**, so anything needing `ddx`/`ddy` is resolved *before* the per-light loop, never inside it. Both shadow kinds compute their depth bias from derivatives, which is why `scene.psh` evaluates every shadow map up front and the loop only indexes the results. A branch on a constant-buffer value is uniform and safe; a branch on the loop's light is not.
- **`Shadows.fxh` passes `ShadowMapAttribs` into its functions, which the converter's header tells you never to do.** It works because none of those functions multiplies by a matrix member — the matrices are only read at the call site. Do not take it as licence to pass structs generally.
- **`TextureCubeArray.SampleCmp` only works from a pixel shader, and fails silently anywhere else.** `GLSLDefinitions.h` maps it to `texture(samplerCubeArrayShadow, …)` inside the `FRAGMENT_SHADER` branch and to the literal `0.0` outside it — "no textureLod for samplerCubeArrayShadow". A cube shadow read from a vertex or compute stage therefore reports *fully shadowed*, with nothing on any output stream. The same holds for `Texture2DArray` and `TextureCube`.
- **A MUTABLE shader variable is set once and cannot be re-set** (`ShaderResourceVariable.h`). The material SRB is built around that: changing a material's textures means creating another material, never re-pointing the one it has.

**Structure**

- **The seam holds, and it is why 3.6 cost nothing.** No Diligent type appears in engine, editor or game code: `rendering/diligent/` is the only directory that includes a Diligent header, and `rendering/renderer.cpp` names `DiligentRenderer` exactly once. Everything else goes through `IRenderer` and the opaque handles. Keep new GPU-facing work behind that line — Phase 8's move off OpenGL is only cheap while it stays true.
- **assimp flips V when it imports a glTF, so `aiProcess_FlipUVs` is mandatory.** Its internal UV origin is the bottom-left; glTF's is the top-left, so `glTF2Importer.cpp` does `values[i].y = 1 - values[i].y` on the way in. The engine samples V down from the top-left, as glTF stores it, so without the flag every imported texture is mirrored vertically against its unwrap. This cannot desynchronize the tangent basis — only V flips, the tangent follows +u, and the bitangent is derived rather than imported.
- **A component reaches its node only through `_owner`, and every add path must set it.** `ComponentsProvider::addImpl` — the path behind `Node::add<T>()` — did not, while all three `addDynamic` overloads did, so a component added in code got a null owner and crashed the moment it touched its `Transform`. Deserialized components were fine, which is why this survived until a toolbar command added one.
- **A texture's colour space is set by hand and by nobody else.** Nothing may write a `TextureAsset`'s own settings — `_withColor`, filter, wrap — on its behalf: the asset is shared between materials and those fields are serialized, so writing them stomps a deliberate choice. This was settled when the model import could have cleared `_withColor` for a normal or ORM map and was **rejected by the project owner**; the import that did that wiring is gone as of the material-asset change, but the rule outlives it. The standing consequence, accepted: **a data map arrives with `_withColor = true` and is sampled through sRGB until someone unchecks it by hand.** The scene's own `scene_normal.png` and `scene_omr.png` are in that state, so lighting there is subtly wrong and is not evidence of a shader bug.
- **A material is a project file, and nothing else is a material.** `MaterialAsset` (a `.mat`) is the only thing that holds a surface; `MeshRenderer` and `SpriteRenderer` hold `MaterialLink`, which names one and owns no surface of its own. A model brings geometry and material *slots* and no materials at all — `MeshAsset::wireTextures` and the importer's `ModelMaterial` were deleted, so **an imported model draws with the default material until a `.mat` is linked per slot.** That was the project owner's call over the alternative of extracting a `.mat` per model material on import; re-propose it only as a deliberate decision, not as a bug fix.
- **An asset's data lives in exactly one of two places, and `Asset::isStoredInOwnFile()` says which.** A texture's settings are in `assets_registry.cnf` (its own file is an image nobody but the loader reads); a material's are in its `.mat`, so a change to one material is a diff of one file. Storing both would be silent data loss: the registry's copy is deserialized after the file's and would win. Two things enforce it — `convert<AssetsConfig>::encode` skips a self-stored asset, and `AssetsDeserializer` only ever restores registry-stored types.
- **A self-stored asset must be read outside a deserialization phase.** `MaterialAsset::loadToMemory` resolves its texture links through the generic deserializer, which *defers* an `ASSET_LINK` while a phase is open — and a deferred link is only ever delivered to a component, so an asset's would be dropped silently. What satisfies this is load order: `restoreEngineAssetsByFiles` runs after `AssetsDeserializer` has closed its phase and before any scene loads. It logs a warning rather than failing quietly if that order is ever broken.
- **The renderer takes geometry, never a description of it.** `createMesh(const MeshData &)` is the only way meshes get to the GPU; generating a primitive and importing a model both happen engine-side, and no Diligent-facing code includes an inspector type or an assimp header. Keeping assimp on the engine side of that line is what lets Phase 9 drop it from the shipped runtime.
- **A material slot from a mesh source is never a safe index into the material list.** Slots come from the imported file; the inspector can shorten the list at any moment without raising a flag. Every draw clamps — `std::min(materialSlot, lastSlot)` in `MeshRendererSystem` — and `getMaterials()` is what guarantees there is a last slot at all.
- **`MeshRenderer::_acquiredAsset` is both the release target and the ownership flag**, and it exists because `_meshAsset` cannot serve as either: the inspector rewrites that field directly, so parts must be given back to the asset they came from, and non-null is also what distinguishes borrowed parts from a primitive this component generated and must destroy itself.
- **A capsule's `height` is its straight section, not its total extent** (total is `height + 2 * radius`). The serialized defaults — height and radius both 1 — are only coherent under that reading, so it cannot be reinterpreted without breaking every saved capsule.
- **Node ids in `.nd` scenes are not arbitrary.** Six hand-written nodes with ids 100–105 crashed scene loading before the first frame with nothing on either output stream; ids 10–15 loaded fine. Cause not chased down — it only matters when authoring scene YAML by hand, but a scene that fails to load for no visible reason should have its ids checked first.
- **`MeshPrimitiveType` is the one enum that does not serialize through `magic_enum`.** `MeshRenderer::serializeMeshData` writes `static_cast<int>` of it into the primitive-data blob. The append-only, delete-from-the-tail rule is the same either way, but the two mechanisms agree only because its enumerators are contiguous from `None = 0` — do not give one an explicit value.
- **raylib and Diligent collide on two names, and the fix is include order plus one guard.** `raymath.h` defines `PI` as a macro and Diligent declares `Diligent::PI`, so any Diligent header reached after raylib fails to parse — `diligentRenderer.h` wraps its `ShadowMapManager.hpp` include in `#pragma push_macro("PI")` / `#undef PI` / `pop_macro`. And `raymath.h` declares `Vector2`/`Vector3`/`Vector4`/`Matrix` *unguarded*, so it has to come after `raylib.h`, never before.
- **Never use bare `include_directories()`** — always `target_include_directories()`, scoped to the target that needs it. A blanket call once made assimp's `texture.h` shadow DiligentCore's `Texture.h`.
- **One `.mat` is one `MaterialHandle`, shared by every slot that links it.** That sharing is the point — an edit reaches all of them — and it is why `MaterialLink` is a plain value type with no GPU state to copy. It is also why a per-renderer material instance is not a checkbox away: a material's texture set is fixed once it exists (the SRB rule below), so `MaterialLink::_isInstanced` is inert until something actually builds a second material.
- **`TextureAsset::acquire()`/`release()` must be paired by whoever stores the handle, and the reference goes back to the asset it was taken from.** Never to whatever an asset-link field names at release time — the inspector writes those fields directly, so they change under the holder. `MaterialAsset` keeps the `TextureAsset *` next to the handle for exactly this, and `SpriteRenderer::_acquiredTexture` is the same trick for the material it builds from its own texture. The registry's eager load at startup is uncounted, so the count governs sharing between materials, not residency.
- **The inspector mutates components without raising `isChangedFromEditor`** — its list `+`/`-` buttons and its asset-link fields write straight through member pointers, and `UiInspector::track` only re-binds the panel. Anything derived from that state has to re-derive by comparison, never by waiting for a flag. `MaterialAsset::getHandle()`, `MeshRenderer::getMaterials()` and `SpriteRenderer::isQuadStale()` are the three places that do.
- **A shadow bias moves the compared point *toward* the light, never away from it.** Depth grows with distance, and the comparison is `LESS`, so a point is lit exactly where its own depth is the smaller of the two. Push it the other way and every caster fails its own comparison — the symptom is a caster uniformly dark with a bright one-texel rim along its silhouette, which is the texels the object no longer fully covers reading the cleared far depth. A surface with `castShadows: false` keeps looking correct throughout, because it is never in the map to shadow itself; that contrast is what names the bug.
- **A slope-scaled bias is measured in shadow-map texels, never in screen pixels.** `ddx`/`ddy` of a world distance give how much of it one *screen* pixel spans, which says nothing about how much depth one shadow texel spans and explodes wherever the camera grazes a surface. The 2D paths take their derivatives of shadow-map UV *and* depth together (`ComputeReceiverPlaneDepthBias`); the cube path has no UV, so it offsets along the surface normal by the texel's own footprint at that distance instead, scaled by the sine of the incidence angle.
- **"Brightest areas dark, edges lit" names a symptom, not a cause.** It is what a failing depth comparison looks like from any direction: a near plane past every caster (6.c) and a bias with the wrong sign (6.d) produced the identical appearance. Read it as "the comparison is failing where it should pass" and check each input, rather than reaching for the previous fix.
- **A shadow projection's near plane is a constant, never a fraction of the light's `range`.** `range` is how far a light *reaches* and is routinely thousands of units; scaling the near plane by it puts the near plane past every caster in the scene. With `DepthClipEnable = False` that does not even fail loudly — the casters are clamped to the nearest depth instead of being clipped, so they occlude everything and the light appears to shade the wrong parts of a surface. The symptom is a lit object whose *brightest* areas are dark while the cone's edges are lit; it was diagnosed from a light with `range = 5000` and a 50-unit near plane.
- **A constant buffer's size and what gets written into it are two separate declarations, and nothing checks them for you.** `MapBuffer` hands back driver memory with nothing behind it, so a struct that outgrew its buffer corrupts whatever the driver keeps there and crashes somewhere unrelated, frames later — camera motion was the visible trigger, and the code that was actually wrong had nothing to do with the camera. `uploadConstants` now refuses a write larger than `GetDesc().Size` and logs it, which is the only reason this class of bug is now loud.
- **A light reaches the shader only through `_visibleLights`, and its shadow assignment travels with it.** The array is rebuilt every frame in `endScene`, before the shadow maps are filled, because the maps have to be rendered before the pass that samples them and the shader has to be told which light owns which map. Ordering only matters past `MAX_SCENE_LIGHTS`, where directional lights win and the rest go by distance minus range. **A frame with no directional caster leaves `iNumCascades` at zero**, which `Shadows.fxh` reads as fully lit rather than as an error — that is the guard, not a branch.
- **A loaded mesh always draws with a valid material** — the linked one, or `Renderer::defaultMaterial()`. This is not politeness: `endScene` skips any draw whose material handle does not resolve, so an unlinked slot would be *invisible* rather than untextured. `MeshRenderer::getMaterials()` keeps the list as long as the source's highest slot (it grows, never shrinks), and `MaterialLink::getHandle()` supplies the default.
- **A component that owns a renderer handle must release it in `onDestroy()`.** That virtual is the only hook between `ComponentChunk::remove` and the slot being reset; `onDispose` runs at engine shutdown only, so anything relying on it alone leaks on every node deletion. `Light` went without one until the bug-hunt pass, and `destroyLight` had **no caller anywhere in the engine** — every deleted light node left a pool slot lit forever with nothing able to name it.
- **A light is the only render resource the renderer keeps between frames, and that changes what "skip" means.** A mesh is re-submitted every frame, so skipping an inactive node stops it drawing. A light is retained, so skipping it leaves the last state applied — a deactivated node whose light carries on shining. Anything else that becomes retained state inherits this rule.
- **The update phase skips inactive nodes at the runner; start-frame and end-frame do not.** `SystemsRegistry::update` has `if (!node->getIsActive()) continue;` — so a system that must observe deactivation cannot be an update system, and its own internal active check will simply never run. That is why `LightSystem` is a start-frame system and why `MeshRendererSystem` carries its own check.
- **Which phase is correct depends on where the resource is consumed, and it is not the same for all of them.** Lights and draws are read by `endScene` at the *bottom* of the frame, so start-frame is right for them and also keeps them sampling the same transforms. The camera is read by `beginScene` at the *top* — and the two hosts disagree on order (`ExampleGame` runs `update` before `beginScene`, the editor runs `beginScene` first). Moving `CameraSystem` to start-frame therefore makes the camera lag a frame in both, which is why the deactivated-camera fix went into `CameraDirector::getActiveCamera()` instead. Do not generalise the light fix to the camera.
- **A component owning a renderer handle needs `noexcept` move operations, and this is enforced by `static_assert`.** `ComponentChunk` grows with `_components.resize(capacity * 2, T{})`, and a vector relocates through `move_if_noexcept`: a move that is not `noexcept` silently falls back to the copy. Since a copy deliberately drops GPU state, that would strand every live handle in the chunk the moment it grew. Note the trap that hides this: every component declares `~T() override = default`, and a user-declared destructor *suppresses the implicit moves* — so before this pass the chunk was already relocating by copy, and only worked because the destructors released nothing.
- **A copy of a render component carries what it is authored with and none of its GPU state**, the same contract `Material` set in Phase 4: handles, acquired-asset pointers and loaded flags are dropped, so the copy resolves its own on the next frame. Copy-assignment releases the destination first.
- **`unload()` reaches the renderer only through `Renderer::isAlive()`.** It runs from teardown and from a `noexcept` move assignment, where `get()` throwing means `std::terminate` rather than an exception.
- **A destructor may only reach the renderer through `Renderer::isAlive()`.** `get()` throws once the renderer is down, and nodes and assets are destroyed after `Renderer::shutdown()` — throwing from a destructor there ends the process.
- **Background work must be waited on explicitly.** A dropped `std::future` does not wait, where a `jthread` destructor did. Every path that frees or recycles a slot a job writes into has to join it first.

## How to work on this

**Build** with CLion's bundled CMake, never a system `cmake` — `find_package` resolves differently between them and has already produced a build that configured under one and failed to link under the other:

```
"D:/Programms/CLion 2026.1.1/bin/cmake/win/x64/bin/cmake.exe" --build <build-dir> --target BreadEditor -j 14
```

One build directory from 3.6 on. The two that existed for the R3D-vs-Diligent diff now configure identically, so whichever one survives is the one to use.

**raylib is a build output, not a black box, and this is how it is produced.** `lib/engine/` holds four headers — `raylib.h`, `raymath.h`, `rcamera.h`, `rlgl.h` — and one `libraylib.dll`, deliberately not a submodule. To change its version or its GL level: clone the tag into a throwaway directory, configure, copy those five files over, delete the directory.

```
cmake -S raylib -B build -G Ninja -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_C_COMPILER=C:/msys64/clang64/bin/clang.exe \
      -DBUILD_SHARED_LIBS=ON -DBUILD_EXAMPLES=OFF -DOPENGL_VERSION=4.3
```

Build it with the project's own clang64. The DLL that results imports nothing but the five Win32 libraries and the UCRT stubs — **compare its import table against the one it replaces**, because anything new appearing there is a second C runtime that would have to ship alongside it. Nothing else needs an import library: the targets link the `.dll` directly.

**Only one build at a time in it.** Two ninja processes in one build directory, or one killed mid-flight, leave **zero-filled `.obj` files** that ninja then considers up to date — so compilation "succeeds" and the link fails with `undefined symbol` for functions that are plainly defined in the sources. Do not go looking for a missing source file or a stale glob: a valid COFF object starts with the bytes `64 86`, a corrupt one with `00 00`, and stray `*.obj.tmp` files nearby confirm it. Delete the corrupt objects and the leftovers and rebuild; no reconfigure is needed.

**"It compiles" and "it launches" prove nothing here.** Every real bug in this migration so far was silent at build time and visible only on screen: a shader that failed to compile, a UI that went black, text that vanished, geometry lit from the wrong side. The acceptance criterion is a screenshot or a pixel measurement, never an exit code. Prefer sampling specific pixel values over reading a full screenshot — it is cheaper and more precise. Read the image only when you do not yet know what you are looking for.

**Delegate broad searches to a subagent.** Anything shaped like "find every use of X", "which file sets Y", or "summarize how Z is done across this tree" — especially across the vendored DiligentCore/DiligentFX/raylib sources — should go to a subagent that reads a lot and returns a few lines. Keep decisions, diagnosis and implementation in the main session: a subagent starts cold and would have to re-read this file and the seam to do them, which costs more than it saves.

**The test scene** (`games/example_game/assets/`) is checked in: a Capsule at `x = -3`, a Cube at the origin with a deliberately non-trivial transform and the scene's three textures, the `scene.gltf` model at `x = +3`, a 40×40 Floor plane, and a directional SunLight — one node per rendering path the migration has to keep working.

**Its lighting was retuned in Phase 6, and the reasoning matters more than the numbers.** It used to be a white background at full ambient energy, which made shadows *mathematically* invisible: the ambient term is `ambientColor · energy · albedo`, so a white ambient at energy 1 already saturates any light surface, and removing the directional term in shadow changes nothing. The background is now a dim blue-grey `(66, 78, 96)` and `_ambient.energy` is `0.35`, with a warm sun at intensity 3 tilted off vertical. Note **the ambient colour is not authored** — `GlobalLightSystem` copies the active camera's background colour into it every frame while the mode is `SOLID_COLOR`, so the camera's `_backgroundColor` in `Root.nd` is the real knob; `energy` is the only ambient field that survives from `global_light_settings.cnf`. The Floor carries `castShadows: false`, which is what stops a ground plane self-shadowing and also exercises the new flag. The Cube's transform is not decorative: with an identity matrix, a wrong per-draw model matrix and no model matrix at all look the same. **To update the scene, edit it in the editor and copy `Root.nd`, `assets_registry.cnf`, `project_settings.cnf` and `global_light_settings.cnf` back out of `bin/assets/game/`** — the build only copies what is absent and will never overwrite build-directory state.

**Code left behind carries no migration narrative.** Comments about phases, about what used to be, or about what will replace this belong in this file or the log, never in a header. A comment earns its place only by explaining something non-obvious about the code as it stands.

**At the end of every session**: update the Status section here, move any newly discovered load-bearing rule into Invariants, and put the incident itself in the log. This pair of files is the only handoff between sessions.

## Context

BreadEngine's rendering is currently 100% OpenGL, locked in via r3d (a PBR renderer built on raylib's rlgl abstraction). There is no path from here to Vulkan/D3D, which blocks the long-term goal of a future-proof renderer for shipping a real game (horror/adventure) on PC and eventually SteamDeck/consoles. DiligentEngine has been chosen as the target RHI (D3D11/D3D12/Vulkan/Metal/GL, plus a GLTF PBR Renderer + deferred shading + SSAO/Bloom in DiligentFX/DiligentSamples). This plan sequences that migration so BreadEngine stays buildable and runnable at every step (strangler-fig, not big-bang), given this is solo part-time hobby work with eventual AI-agent assistance on implementation, while architectural decisions stay with you.

## Phase 0 — settled

The four spikes are done; their findings are in the log. What they settled, and what still holds:

- **Windowing stays raylib.** It keeps the window and input; Diligent takes the device. Proven to coexist on one HWND.
- **The editor's 2D chrome stays raylib/raygui/rlgl permanently.** The editor never ships — only the 3D viewport content and gizmos move to Diligent. This deliberately avoids rewriting a 26-file UI toolkit that has nothing to do with the goal.
- **The editor process runs Diligent's OpenGL backend** so the scene is a plain GL texture the viewport can blit without a copy. CPU readback is the recorded fallback if that ever stops being possible — see Phase 8.
- **~~`PBR_Renderer` is the integration target~~ — reversed by Phase 3.5.** Both it and `GLTF_PBR_Renderer` are reference-only; the engine's own shader is the integration target, and BreadEngine's asset pipeline is not reshaped around glTF's loader.

## Phases 1–9 — Backend cutover (feature parity with today's R3D rendering)

Each phase keeps the tree buildable. Phases 2–3 kept R3D alive behind the new seam via a `BREAD_RENDER_BACKEND` switch so regressions could be caught by screenshot-diffing the same scene under both backends; 3.6 removed both the switch and R3D. That QA method — looking at the scene rather than at an exit code — is what substitutes for not having a rendering engineer's eye, and it outlives the reference it started with.

1. **Build system.** Add DiligentCore/DiligentTools/DiligentFX as git submodules (Diligent's documented approach — its CMake uses custom macros that plain `add_subdirectory` handles better than `FetchContent`), wired in alongside the existing vendored raylib/r3d/assimp blocks in root `CMakeLists.txt` — remove nothing yet. Collapse the three duplicated DLL-copy blocks (root/editor/example_game) into one reusable CMake function while here.
2. **Insert the seam.** New `modules/engine/rendering/IRenderer.h` + opaque handle types (`MeshHandle`, `MaterialHandle`, `TextureHandle`, `LightHandle` — plain index/generation structs, not per-object virtual dispatch, since only one backend is active at a time). Move every R3D call site (`meshRendererSystem.cpp`, `lightSystem.cpp`, `globalLightSystem.cpp`, `textureAsset.cpp`, `material.cpp`, `meshRenderer.cpp`, `spriteRenderer.cpp`, `editor.cpp`, `example_game/main.cpp`) into one `R3DRenderer : IRenderer`. Components (`MeshRenderer`, `SpriteRenderer`, `Light`, `Material`, `TextureAsset`, `Camera`) hold handles, not raw R3D types. **Before touching `Light`/`Material`: confirm whether `.yaml` scene files bake `R3D_LightType`'s numeric enum value** (check `BaseYamlConfig`/inspector serialization) — if so, either keep the enum's underlying values stable across the swap or write a one-time migration for existing scene assets. This phase should be a pure refactor with zero visual change — validate with a before/after screenshot diff.
3. **DiligentRenderer MVP.** Forward-shaded (not deferred) single PBR pipeline: PSO + SRB, one directional light, no shadows/IBL/post yet. Wire the existing `Camera3D`/`rcamera.h` math into Diligent's per-frame constant buffer (matrix-convention conversion is the only new math needed). Milestone: a textured lit cube renders equivalently via both backends. This is where the "not a rendering engineer" learning curve is steepest (PSOs/SRBs are conceptually unlike raylib's globals-based rlgl API) — budget accordingly, and treat DiligentSamples Tutorials 01–05 as the reference path.
3.5. **`PBR_Renderer` adoption — DECIDED: not adopted.** *(numbered .5 on purpose: renumbering 4–11 would invalidate every cross-reference in this document.)* The engine keeps the metallic-roughness shader 3.c wrote, and **spike 0.4's "drive `PBR_Renderer` directly" is reversed**: it is reference-only from here. The spike's measurements are in the log; what the rest of this plan depends on:

   **DiligentFX is adopted component by component instead.** Most of it does not go through `PBR_Renderer` at all, so refusing the renderer costs far less than refusing the library. The list is explicit so it does not get re-argued every phase:
   - **Phase 6** — `Components/ShadowMapManager.hpp` for CSM, with `Shaders/Common/public/PCF.fxh` and `Shadows.fxh` included into the engine's own shader.
   - **Phase 7** — `PostProcess/` (Bloom, DepthOfField, ScreenSpaceAmbientOcclusion, ScreenSpaceReflection, TemporalAntiAliasing), `Components/ToneMapping.hpp`, and `Components/EnvMapRenderer.hpp` for the skybox.
   - **Phase 8** — `Components/CoordinateGridRenderer.hpp` is what the grid becomes when it moves out of rlgl and into the renderer as real scene geometry.
   - **Not available without `PBR_Renderer`, and therefore ours to write:** the IBL precompute (its `PrecomputeCubemaps` is a method on the renderer, though the shaders it drives — `PBR/private/ComputeIrradianceMap.psh`, `PrefilterEnvMap.psh` — are usable directly), order-independent transparency, and the glTF extension lobes (clearcoat, sheen, anisotropy, iridescence, transmission).
   - Including a DiligentFX `.fxh` from an engine shader needs `CreateCompoundShaderSourceFactory({&DiligentFXShaderSourceStreamFactory::GetInstance(), <the file factory>})` — its shaders are compiled into the static library, not shipped as files.

   **What the decision releases.** The deadline this phase existed to meet — settle the conventions before Phase 5 writes six generators — is met by keeping them: `MeshVertex` and the material struct stay as they are, and **Phase 5 is unblocked with no changes to either**.

3.6. **Remove R3D — DONE.** *(new after 3.c.)* Pulled forward from Phase 9 on the reasoning that less code is less to break, once the R3D screenshot diff had served its purpose. It was mechanical, as Phase 2's seam promised; the log has what was deleted and the two decisions taken along the way (the backend switch removed outright with the renderer moved up to `rendering/diligent/`, and `applyDefaultEnvironment` dropped in favour of engine-owned field initializers). `Slope`, `Torus` and `FreePoly` were dropped here too, ahead of Phase 5.

   ⚠️ **The capability cost was accepted deliberately and is partly paid back.** Deleting R3D could not break the Diligent build, but it did remove the only configuration in which the editor was *complete*. **Phase 5 restored models and all the primitives**; skybox and cubemaps, ambient/IBL maps, every post-effect, shadows and all lighting past one directional light are still stubs until Phases 6–7 land.

   **rlgl and assimp did not go with it.** Phase 9 pairs "remove R3D" with "remove rlgl", but the renderer is *built on* rlgl interop by design (Phase 0.3's GL sharing, 2.d's overlay brackets, 3.a's framebuffer over Diligent's textures, 3.b/3.c's state restores). rlgl is load-bearing and stays; Phase 9 keeps that half, and with it the open question of who owns the shipped game's 2D. assimp is scoped to import-time in Phase 5 and was untouched here.

4. **Materials & textures cutover.** Replace `TextureAsset`'s raw `Image`/`Texture2D`/`R3D_Cubemap` members with `TextureHandle` (DiligentTools' `TextureLoader` loads PNG/JPG/HDR/KTX/DDS straight into an `ITexture`, likely a cleaner reuse point than raylib decode + manual upload — confirm in Phase 0.4). Replace `Material`'s `R3D_Material` wrapping with an engine-native albedo/normal/ORM/emission struct shaped to glTF's metallic-roughness convention, since `meshAsset`'s existing texture-slot auto-wiring already approximates it.
   **DONE.** Phase 2 did the `TextureHandle` and engine-native `Material` half, 3.c adopted `TextureLoader` and built the material texture binding, and Phase 4 closed it with the per-material SRB behind `MaterialHandle` and acquire/release refcounting in `TextureAsset`. See the log for the ownership decision and its copy rule.
5. **Mesh primitives, MeshRenderer, SpriteRenderer — DONE.** All six remaining generators (sphere, hemisphere, cylinder, capsule, plane, quad) landed on top of the cube from 3.b, sharing two helpers: `appendGrid` for every flat rectangle including the box's six faces, and `appendRevolution` + `appendCap` for everything spun around Y. The `forward` parameter stayed, as planned — `Quad` is its remaining user. The assimp import landed as `rendering/geometry/modelImporter.{h,cpp}`, and the seam moved with it (see Status and Invariants). The log has the three decisions, the flattening choice, and the two false alarms the white-on-white test scene produced.

   **Deferred out of this phase, deliberately:** the on-disk cached mesh format. Import is in-memory per run; the geometry is uploaded and the CPU copy dropped. Worth doing when there are enough models for startup time to be measurable, and it needs versioning against `MeshVertex`.
6. **Lights — COMPLETE.** `lightSystem.cpp` pushes every light through `IRenderer`; the forward shader loops a fixed-size array of them (6.a); DiligentFX's `ShadowMapManager` gives four directional cascades (6.b); each shadow-casting spot gets a slice of its own array (6.c); each shadow-casting omni light gets a cube of a cube array, six 90° depth passes (6.d). The log has the sub-phase split, the conventions that had to be reconciled with DiligentFX, and the four defects found afterwards.

   6.d. **Omni shadows — DONE.** The first shadow kind with no DiligentFX component behind it: `ShadowMapManager` fits cascades to a camera and `PCF.fxh` filters a 2D map, so the cube array, its six passes and its filtering are all engine code. Four casters at 512² faces, a five-tap disk whose radius `shadowSoftness` drives. What is worth knowing before working near it:
   - **The shader is given no matrix and no face index.** A 90° projection writes `depthScale - depthScale·near/d` where `d` is the distance along the face's forward axis — which for any point inside that face's frustum is exactly the largest component of the direction to it. So two coefficients per light replace six matrices, `TextureCubeArray.SampleCmp` picks the face from the direction, and nothing has to reconstruct which projection applied. The expression is API-agnostic: NDC ranges differ between GL and D3D, the window depth a given distance produces does not.
   - **`renderShadowCasters` was reused with no change**, six times per light — it already took a target view and a `float16` world-to-light-clip, which is what a cube face needs.
   - **The six face view matrices are a table and not a derivation.** raymath's right-handed `MatrixLookAt` with up = −Y for ±X and ±Z, +Z for +Y and −Z for −Y. These are the vectors that orient each face image the way the hardware's own direction-to-texel rule reads it back; the intuitive ones are wrong, and a wrong one mirrors a face without failing anywhere.
   - **Nothing outside `rendering/diligent/` changed.** `Light` already showed `withShadows` for every type and `lightSystem.cpp` already forwarded it.
   - ⚠️ **Both bias rules in Invariants were paid for here** — direction, and units. A cube gives the near-plane mistake six chances too; that one was avoided.
7. **Environment / post-processing / skybox.** Cleanest phase given the existing abstraction: the parameter blocks in `configs/light/` (background/ambient/ssao/ssil/ssgi/ssr/bloom/fog/dof/tonemap/color) are already engine-native and serialized, and `setEnvironment` is the single place that has to start mapping them onto DiligentFX PostFX settings instead of reading three of them — `globalLightSystem.cpp` call sites shouldn't need to change. `R3D_GenProceduralSky` has no Diligent equivalent (it's an analytic sky shader, not an HDRI) — port a known public model (Preetham or Hosek-Wilkie) as an HLSL shader. Close the previously-stubbed Cubemap/Custom skybox modes now that Phase 4 gives a real texture/cubemap pipeline to hang them on.

   **Phase 6 leaves one thing at this door:** `GlobalLightSystem` currently copies the active camera's background colour into the ambient term every frame while the mode is `SOLID_COLOR`, which is a stand-in for the environment this phase is meant to provide. Whatever replaces it has to keep the shadow verification method working — a shadowed floor reading *exactly* the ambient-only value is what several of Phase 6's checks are built on.

   ✅ **The GL-version question that used to sit here is answered.** It was: DiligentFX's BRDF LUT precompute uses `bitfieldReverse`, which needs GLSL 400, and IBL needs that LUT. 6.d needed cube map arrays for the same underlying reason, and the third of the three options put up here — rebuild the vendored raylib as `GRAPHICS_API_OPENGL_43` — was taken then. So the LUT compiles as written, the compute-based PostFX components have compute, and nothing in this phase has to work around a 3.3 ceiling.
8. **Editor viewport integration.** Implement whatever Phase 0.3 spiked (GL-sharing or readback) so `viewportWindow.cpp`'s `R3D_SetResolution`/`DrawTexturePro` pattern becomes Diligent-scene-into-raygui-panel. Leave `raygizmo.c` (confirmed rlgl-based: `rlBegin`/`rlVertex3f`/`rlGetMatrixModelview`) as a raylib/rlgl overlay drawn after the Diligent blit into the same panel — continuing the existing compositing pattern rather than porting a third-party gizmo lib.

   **The GL half of this already landed early, in 2.d and 3.a**, and works: the renderer owns the scene target, `drawSceneTexture` blits it into the panel zero-copy, and the overlay brackets put rlgl's grid and gizmos into Diligent's own colour and depth attachments. What is actually left for this phase is the part below.

   ### What a non-GL backend costs the editor

   Consolidated here on purpose — these consequences were previously scattered across 0.2, 0.3 and 2.d and could not be seen together. Nothing here needs doing until the runtime actually moves off OpenGL; it is recorded so the cost is known in advance rather than discovered.

   - **The shipped game is unaffected.** It never calls `beginSceneOverlay`/`endSceneOverlay` and never blits into a panel — it renders the scene and presents. Moving it to Vulkan/D3D is a matter of implementing device and swap-chain creation in the backend instead of `AttachToActiveGLContext`.
   - **The editor's 2D chrome is unaffected either.** raygui keeps drawing through raylib's own GL context regardless of what renders the viewport; spike 0.1 ran raylib-GL and Diligent-Vulkan on the same HWND for 60 frames with no conflict. Phase 0.2's "keep raylib/raygui forever" decision survives a backend change intact.
   - ⚠️ **Exactly one seam breaks, and it breaks in two places — both in the viewport.**
     1. **Zero-copy delivery has no non-GL equivalent.** Today `ITexture::GetNativeHandle()` returns a GL texture name that gets wrapped as a raylib `Texture2D`. Under Vulkan/D3D there is no shared GL object. Fallback is the one spike 0.3 already named: CPU readback — slow, but acceptable for a preview pane. API-specific interop extensions are the faster alternative and considerably more work.
     2. **The depth-shared overlay stops being possible at all.** The grid and gizmos currently draw through rlgl *into Diligent's own depth buffer*, which only works because `rlLoadFramebuffer` can be pointed at Diligent's GL texture names. Without GL there is nothing to point it at. **The fix is the one 2.d's depth trap already identified as the better long-term answer regardless: the grid moves into the renderer as real scene geometry, and gizmos draw on top after the blit.** A grid is scene content, so this is a correction rather than a loss.
   - **D3D has a separate, earlier blocker that has nothing to do with rlgl:** DiligentCore's `try_compile` check for `atlbase.h` fails on this toolchain (MSYS2 clang64 ships MinGW-w64 headers, which have no ATL), so `D3D11_SUPPORTED`/`D3D12_SUPPORTED` are false. Vulkan+GL is what this toolchain can build; D3D needs a separate MSVC toolchain first. See spike 0.1.

   ⚠️ **Rejected, so it does not get re-proposed: keeping the editor permanently on Diligent-GL while the game ships Vulkan/D3D.** It is technically the cheapest path — the whole seam above keeps working untouched — and it was turned down by the project owner on the grounds that matter more than cost: **the editor viewport has to show the game as the shipped build renders it, one to one or as close as achievable.** A permanently different device path means shader and PSO divergence between the two would only ever surface in the game build, which defeats the point of having a viewport. The actual approach (readback, interop extensions, or something else) gets chosen when the move off OpenGL is actually on the table; it is deliberately not being decided now.
9. **Remove rlgl from engine+game.** **The R3D half of this phase moved to Phase 3.6** — what is left is dropping rlgl from engine/game code and `ASSIMP_DLL` from CMake (if Phase 5 scoped assimp to editor-only). This is the harder half: the Diligent backend's GL interop is written on rlgl, so removing it means the shipped game stops sharing raylib's context and owns a swap chain directly. Editor keeps raylib/raygui/rlgl for its own chrome per Phase 0.2.
   ⚠️ **Gap found in 2.d — the shipped game's 2D has no owner in this plan.** Phase 0.2 keeps raylib/raygui only for the *editor's* chrome, and this phase strips rlgl from the game — but the game draws its own HUD with raylib 2D (`DrawText`, `DrawFPS`) and has no replacement anywhere in Phases 1–11. A real horror/adventure game needs a HUD, menus and text, so this is a genuine missing subsystem, not a detail: either a Diligent-drawn 2D/UI layer for the runtime, or an explicit decision to keep raylib in the shipped game for 2D only (which conflicts with the SteamDeck/console dependency-trimming goal). **Decide before Phase 9, since that is where the game loses rlgl.** `example_game`'s currently-invisible 2D (see the 2.d notes) is the first thing that should be re-tested once this lands — it is the existing smoke test for it.

## Phases 10–11 — Greenfield (no porting burden, new subsystems)

10. **Skeletal/bone animation.** No existing BreadEngine code to port (confirmed zero hits for Animation/Skeleton/Bone). Use DiligentFX's `GLTF_PBR_Renderer`/DiligentSamples' GLTF viewer skinning support as the reference (joint indices/weights, joint matrix buffers, GPU skinning) rather than inventing it from scratch. Extend the Phase 5 assimp importer to bake skeleton hierarchy + bind pose + clips. This is a full subsystem (importer + runtime pose blending + GPU skinning + any editor preview tooling) — the GPU-skinning mechanics are well-referenced (good AI-assist fit), but animation runtime design (blending, state machines) is new architecture only you should own.
11. **Shader scripting/authoring.** Fills the two currently-dead placeholder fields (`MaterialAsset::_shaderPath`, `GlobalLightSettings::_skyboxShaderPath`). Diligent shaders are HLSL, cross-compiled via DXC to SPIRV/GLSL/MSL, with `IShaderSourceInputStreamFactory` for `#include` resolution — a natural foundation. Compile user HLSL fragments into fixed material "shader slots" at runtime; hot-reload by watching file mtime and recreating the affected `IPipelineState` (cheap in Diligent, a common pattern). Scope is your call: a fixed-uniform HLSL-snippet system vs. a node-graph editor are very different sizes — the compile/hot-reload mechanics are good AI-assist material, but the authoring UX is a first-party design decision.

    **A shader is an asset, and that is where this phase starts.** Requested by the project owner while material assets landed, and the shape follows from them:
    - **One file per shader, not two.** `scene.vsh` and `scene.psh` are one shader split across two files today. The asset is a single file holding both stages, so a shader is one thing in the project tree, one thing to link, and one thing in a diff.
    - **Its fields draw in the inspector, the same way a component's do.** Not a text field naming a path — the asset's own parameters go through `INSPECT_FIELD`/`INSPECTOR_BEGIN` and render in the property panel like any other inspected struct. What those fields *are* is the open question this phase has to answer: a fixed set the engine declares, or a set parsed out of the shader source. That choice decides how much of the inspector system has to grow (today a `Property` list is built once per *type*, statically — per-*asset* fields are new ground).
    - **`MaterialAsset` links it like it links a texture.** `_shaderPath` becomes a `ShaderAsset *` asset-link field, so it resolves, serializes and shows a picker for free, exactly as the four texture slots do. Which means a material's `.mat` names its shader by guid, and the material rebuilds when the link changes — the same comparison-based invalidation `getHandle()` already does.
    - **It inherits the material-asset rules**: the shader's own data belongs in its own file (`Asset::isStoredInOwnFile()`), and it must be read outside a deserialization phase if it links anything itself. See Invariants.

## Cross-cutting notes

- **Genre priority:** for horror/adventure, shadow quality (point/spot, not just directional) and post-processing (bloom/DOF/fog/color grading) likely matter more to final look than deferred shading or high light counts. Treat deferred shading (via Diligent's render-passes/subpass pattern) as an optional upgrade after Phase 9, not a Phase 3 requirement — don't conflate "reach parity with today's R3D rendering" with "modernize further."
- **Assimp** should end up import-time/editor-only after Phase 5, removing it from the shipped game's runtime dependencies — a free win for the SteamDeck-shipping goal.
