### Renderer decomposition — one class becomes four

Ran between 7.e and 7.f, on the owner's call, because 7.f adds a second render target to the scene pass and every one of its knobs would have gone onto a class that already held four subsystems' pipelines, buffers and textures as its own members. The five translation units were a mechanical split of *one* class: `diligentRenderer.h` was **609 lines** and was the hardest file in the backend to read. It is now **209**, and `ShadowPass`, `EnvironmentMaps` and `PostChain` are members of `DiligentRenderer` with their own headers beside it. No translation unit was added — each sub-object lives in the `.cpp` its code already occupied.

**The order was chosen by how much of the renderer each one still had to touch, cheapest first**, and the gate ran after each: `PostChain` (it reaches only the scene target and its own), then `EnvironmentMaps`, then `ShadowPass` last — the scene pipeline binds its three arrays as *static* shader variables, so the initialization order is a correctness constraint rather than a preference. That constraint is now an Invariant, in the shape it actually takes: `initializeMaps` before the scene pipeline because the pipeline binds what it allocates, `initializePipeline` after it because the depth pass uploads a caster's model matrix through the buffer the scene pipeline created.

**What a sub-object holds and what it borrows** turned out to be the whole design, and it is the same answer three times. Device and context are borrowed pointers — the renderer outlives all three and shuts them down before releasing either. The scene's colour, depth and output textures are **handed in per call and never kept**, because they are reallocated whenever the target resizes and a stored copy would outlive them. `ShadowPass` extends that to geometry: the frame's draws and the mesh pool arrive as one `ShadowCasters` — a `span` and a reference — so the shadow pass walks the renderer's own list instead of being handed a copy of it. That is what kept the split free of adapter code: no list is built for the shadow pass, and nothing is copied per frame.

**Three things moved into `diligentInternal.h`, all for the same stated reason** — more than one concern now reads them. `MeshSlot` and `DrawItem`, because both geometry passes draw from them; `VisibleLight`, because the shadow pass writes the assignments and `uploadLights` reads them; and `MAX_SPOT_SHADOWS`/`MAX_OMNI_SHADOWS` alongside `SPOT_SHADOW_RESOLUTION`, because `scene.psh` is *compiled against* those three as macros and sizes its own arrays from them. The shadow map format, the cascade count and both near planes stayed in `diligentLighting.cpp`, where they still have one reader.

**The `PI` guard is not a per-directory thing, it is a per-include thing.** `diligentInternal.h` pops the macro back after its own includes, so a translation unit that reached raylib first is holding it again by the time it reaches `diligentShadowPass.h` — which includes `ShadowMapManager.hpp` and needs the guard of its own. Found while moving that include out of `diligentRenderer.h`, where it had been since Phase 6.

**Gate: `diff.ps1` IDENTICAL on all three steps** — for `ShadowPass`, 0 of 3,504,640 pixels differing, max delta 0, against the capture the `EnvironmentMaps` step ended on. Worth recording *what that capture actually exercises*, because it is more than it looks: the test scene's `Test Light` is a shadow-casting **spot**, so a zero diff covers the cascade path and the spot path together. The omni path is the one the scene never reaches. It was covered separately by flipping that light's `lightType` to `2` in the build directory's `Root.nd` and running it — both casters throw soft shadows away from the light, with no acne and no self-shadowing — then restoring the file. Anyone touching the cube path again has that as the cheapest way to reach it.
