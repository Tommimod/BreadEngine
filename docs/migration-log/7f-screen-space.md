### Phase 7.f — ambient occlusion and screen-space reflections

Five decisions to the project owner before a line was written, because each one changes the frame graph rather than the code inside a pass.

- **Engine-native passes, not DiligentFX's `ScreenSpaceAmbientOcclusion` / `ScreenSpaceReflection`.** This was the phase the plan reserved for pricing `PostFXContext` on SSR's merits, since SSR is the one effect that genuinely wants motion vectors. The price did not move: `PostFXContext::Execute` still dereferences `pPrevDepthBufferSRV` and `pMotionVectorsSRV` unconditionally (`PostFXContext.cpp:292-298`), so both would have to be produced before either component runs. SSAO is seven passes on top of PostFXContext's four and SSR another seven, and both are temporally accumulated — without real motion vectors every moving object ghosts, and the engine has no per-object motion at all. Camera-only vectors are derivable from depth and a previous view-projection, but that only covers static geometry. Both components also replace the authored parameter blocks with their own attribs structs (`EffectRadius`, `DepthMIPSamplingOffset`, `TemporalStabilityFactor`…). Written here, SSAO is three passes, SSR is one, and all thirteen authored fields keep their meaning.
- **Occlusion darkens the ambient light alone**, through a second scene target holding the ambient term on its own. The alternatives were a depth prepass feeding the scene pass an occlusion map — correct, but a second geometry submission and normals derived from depth rather than from the normal map — and multiplying the whole frame, which is cheapest and darkens direct light with it. The chosen shape costs one RGBA16F target and one pass, keeps one geometry pass, and needs no second resource binding per material.
- **Reflections replace the ambient specular rather than adding to it.** The scene pass has already reflected the sky off every surface; adding a screen-space reflection on top double-counts it, most visibly exactly where SSR is most visible.
- **The G-buffer's fourth channel holds the finished specular weight, not metalness.** This came out of working the arithmetic and went back to the owner as a second question. An octahedral normal takes two channels and roughness a third, leaving one for five numbers' worth of surface. With metalness there, the reflection pass can re-derive `f0` and sample the BRDF table, but the material's ORM occlusion is not recoverable — so it would over-remove wherever an occlusion map darkens the ambient, which is true of both of the test scene's ORM maps. Storing `(luminance(f0) * brdf.x + brdf.y) * occlusion * energy` — the exact scalar the scene pass scaled its reflection by — makes the removal exact, and costs the reflection pass its BRDF table, its Fresnel term and its `nDotV` entirely. What is lost either way is a coloured metal's tint, which does not fit in one channel.
- **SSGI and SSIL pruned.** Both were parameter blocks with no implementation behind them and no plan to acquire one; the append-only serialization rule was lifted for `configs/light/` for the duration of Phase 7, so the blocks are gone from the structs, the inspector and `global_light_settings.cnf` alike. Depth of field stays declared and stubbed.

**What it is.** The scene pass now writes three targets — colour, the ambient term alone, and the surface (octahedral normal, roughness, specular weight) — and everything downstream of it writes colour alone, so the background pass rebinds to one target before it draws. Then `occlusion.psh` samples a cosine-weighted hemisphere per pixel, rotated by interleaved gradient noise; `occlusionBlur.psh` averages nine texels of that, weighted by how close each tap's own distance from the camera is to the centre's; `occlusionApply.psh` writes `ambient * (1 - access)` through a reverse-subtract blend, which is what makes this ambient occlusion rather than a darkening. `reflections.psh` marches the reflected ray in world space, bisects the step that crossed a surface, and writes `(hit - reflected) * weight * access * confidence` additively — signed, which only the floating-point scene target can hold. It multiplies by the occlusion because the ambient in the target has already been darkened by it, which is also why the two passes are in that order and in one class.

**Two things broke, both at startup, both worth recognising again.**

- **Creating into a `RefCntAutoPtr` that still holds an object kills the process.** One pair of shader handles was reused for four pipelines; Diligent logs *"Overwriting reference to existing object may cause memory leaks"* as a debug assertion in `CreateDeviceObject` and the process is gone before the first frame. The log ends immediately after the OpenGL attach line with nothing else on either stream, which reads exactly like a crash inside device creation.
- **A diagnostic that drops a resource walks straight into the dead-code-elimination trap.** Replacing the reflection pass's output with a hit mask made the shader stop depending on the scene colour, the cube, the occlusion and the surface target — the GLSL compiler removed all four, `GetVariableByName` returned null, and the unguarded `->Set()` took the process down. This is the trap `scene.psh` already carried and the tools README already warned about, reached this time by editing a shader in `bin/` with no rebuild. The fix is in the code rather than in the diagnostic: every texture in this file binds through a `bindTexture` helper that tolerates a name the compiler dropped. Redone with each value kept alive by a vanishing term, the hit mask showed clean mirror images of the capsule and the scooter on the floor — which is what confirmed the march finds real geometry rather than only self-intersections.

**The refactor gate, and why three pixels moved.** With both effects switched off the frame should have been bit-identical to the pre-change build. It differed in **3 pixels of 3,504,640, all by 1 in blue** — and by this project's own rule that is a regression until explained. Two captures of the baseline diffed to zero, so the capture path was not the source. What closed it: adding the same `specularWeight` arithmetic to the *baseline* shader with its result multiplied by `1e-30` — a contribution that cannot change any value — reproduced **exactly those three pixels with exactly those deltas**. The frame-graph change contributes nothing; giving `brdf` and `occlusion * energy` a second consumer is enough for the GLSL compiler to reassociate the ambient expression, and a relative change of order `1e-7` flips an 8-bit output only where a value sits within a fraction of a rounding boundary. Worth remembering before the next gate: **a handful of pixels at delta 1 after adding an output to an existing shader is arithmetic, not a bug — but prove it that way rather than assuming it.**

**Verified.**

| check | expected | measured |
| --- | --- | --- |
| both effects off, against the pre-change build | identical | **3 of 3,504,640 pixels at delta 1**, explained above |
| the same capture twice | identical | **IDENTICAL** — the path has no noise |
| occlusion on, with `ambient.energy` at 0 | identical, since there is no ambient light to remove | **IDENTICAL**, 0 of 3,504,640 |
| occlusion on, normal scene | contact darkening only | **1.74%** of pixels, max delta 33 — under the capsule, under the deck and wheels, in the scooter's crevices; nothing on open floor or sky |
| reflections with `maxDistance` at 0 | identical, since no ray can travel | **IDENTICAL**, 0 of 3,504,640 |
| reflections on, normal scene | only surfaces under the roughness gate | **0.69%** of pixels, max delta 35 — the stem, the deck, the wheel hub and the body, nothing else |
| the rlgl boundary, both effects on | silent | **silent** — the two new blend states are put back by the existing `yieldToRaylib` |

The `maxDistance = 0` result is the one that proves the swap arithmetic: with no hit the pass writes zero, so the removal and the addition cancel exactly rather than approximately. The editor was captured with both effects on — viewport, grid overlay, gizmo chrome, asset tree and console text all intact through the resize path that rebuilds all three targets.

**Left as a shader constant rather than an authored field.** `REFLECTION_MAX_ROUGHNESS` (0.5) is where a marched ray stops standing in for the prefiltered cube — past it the cube is both blurrier and more correct — and `REFLECTION_DISTANCE_FADE` (0.25) is how much of the ray's range the reflection fades out over, without which a large flat surface reflects up to a circle drawn in mid-air. Both are art direction and both could become fields; neither was, because the owner's answer fixed the field set and a constant is cheaper to promote later than to remove.
